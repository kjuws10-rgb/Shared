## 성공과 보존을 구분할 것

- TryWrite 성공: 메모리 큐에 들어간 상태입니다. 디스크에 저장됐다는 뜻은 아닙니다.
- Flush 완료: 앞선 큐 항목이 처리 경계까지 갔습니다. 오류 속성을 함께 확인해야 합니다.
- 장치 명령 성공: 로그 성공과 별개의 사실입니다. Station·Vision 응답과 측정 결과 파일로 확인합니다.
- 로그 파일 존재: 모든 이벤트가 들어 있다는 보장은 없습니다. 누락 경고·기간·원본 통신 기록을 같이 확인합니다.

## 필요한 후속 결정

1. 운영자가 InterfaceLogError/SequenceLogError를 즉시 알 수 있는 표시와 확인/복구 절차를 정합니다. 현재 직접 소비자는 Flush/Stop 중심이며 상시 경고 UI를 이번 diff에서 추가한 것은 아닙니다.
2. 로그 보존 일수·디스크 여유 기준·아카이브/반출 정책을 정합니다. 실제 고객 자료·자격정보는 승인된 범위에서만 취급합니다.
3. 로그 실패 후 Recipe/Setting 저장을 무조건 재시도하기 전에 현재 저장값을 읽어 확인합니다.
4. PM 비정상 종료 후 잠금 복원이 필요한지는 별도 요구사항으로 확정합니다. 현재 이력 저장과 메모리 LOCK은 다른 기능입니다.


## Setting 디스크·캐시 경계 추가 확인

CSettingFile은실제설정을저장·재검증한뒤로그를쓰며로그예외는전파될수있습니다. CSettingManager는settingFile.Save가정상반환한뒤에만캐시를교체하므로로그실패시디스크는새값·캐시는옛값일가능성이있습니다. 이는정적연결위험이며전체Setting/UI재현합격으로주장하지않습니다. [캐시게시순서](https://github.com/kjuws10-rgb/A3Drilling/blob/334b3599651b2e8e0181fd4459bafaf3cddafff3/Drilling.Common/Managers/CSettingManager.cs#L151-L154).
