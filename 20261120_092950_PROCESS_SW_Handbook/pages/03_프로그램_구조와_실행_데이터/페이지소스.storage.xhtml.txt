<p>화면은 조작과 표시를 맡고 Manager는 조건과 상태를 관리하며 Station은 준비·실행 순서를 연결한다. 같은 장치와 데이터를 여러 화면이 공유하므로 값이 어디에서 만들어지고 언제 실행 사본으로 고정되는지를 알아야 수정의 영향을 판단할 수 있다.</p>
<h2>시작 시 객체가 연결되는 방식</h2><p>시작부는 설정 위치를 결정하고 Recipe·Setting·Product·Review 결과·보정·실행 파일을 다루는 저장 객체를 만든다. 이 객체들을 CManager에 전달하고, 같은 Manager가 가진 Station·Interface·Motion·Review 등을 RootView와 메뉴에 연결한다.</p><p>Manager는 공유 데이터와 서비스의 연결 지점이다. Station은 기판 단위 준비와 실행을 진행하고, Interface·Motion 등의 장치 경로를 사용한다. 화면에서 값을 표시하는 일과 장치 명령을 완료하는 일은 이 책임 구분을 따라 확인한다.</p><p><ac:image ac:width="1200" ac:alt="시작부와 화면·Station이 같은 관리 객체를 공유하는 관계를 보여준다."><ri:attachment ri:filename="p17_03_객체_연결.png"/></ac:image></p><p><em>CAppStartup에서 공유 객체를 조립한 뒤 RootView와 각 기능으로 전달되는 화살표를 따라 읽는다. 모든 선이 장치 명령의 실행 순서를 뜻하는 것은 아니다.</em></p>
<h2>이번 기판의 실행 사본</h2><p>준비 시점에는 Recipe 사본에 장비 설정과 유효한 보정을 합쳐 이번 기판의 가공 모델을 만든다. 여기서 Head별 계획과 실행 파일이 만들어지므로, 준비 후 화면을 편집했다고 이미 만들어진 좌표와 파일이 자동으로 새 값이 되는 것은 아니다.</p><p>실행 사본을 고정한다는 것과 그 사본의 실행을 계속 허용한다는 것은 별개다. 현재 프로그램은 실행 전에 준비 당시의 Review 보정본과 현재 보정본의 파일·저장 시각을 비교한다. 준비 뒤 보정본이 교체되거나 되돌려져 일치하지 않으면 다시 준비하도록 요구한다.</p><p><ac:image ac:width="1200" ac:alt="편집값과 준비 사본의 수명이 다르다는 점을 설명한다."><ri:attachment ri:filename="p19_03_B.png"/></ac:image></p><p><em>준비 화살표를 지난 값이 실행 사본이다. 아래의 끊긴 편집 경로는 나중 편집이 사본을 직접 바꾸지 않음을 뜻하며, 보정본 변경 후 실행에는 재준비 검사가 따른다.</em></p>
<h2>문제가 생긴 값을 어느 계층에서 볼 것인가</h2><p>같은 이름의 값이라도 화면 입력, 저장 파일, Manager 캐시, 실행 사본, 장치 실제값은 서로 다른 시점의 자료일 수 있다. 기판·Recipe·Head와 준비 시각을 맞춘 뒤 값이 달라지기 시작한 경계를 찾는다.</p><table class="wrapped"><tbody><tr><th>계층</th><th>판단할 내용</th></tr><tr><td>화면·입력</td><td>보고 있거나 편집하는 대상이 무엇인가</td></tr><tr><td>파일·Manager</td><td>저장·재로딩한 조건과 현재 캐시가 무엇인가</td></tr><tr><td>Station·실행 사본</td><td>이번 기판에 어떤 조건과 보정본을 준비했는가</td></tr><tr><td>장치·결과</td><td>어느 대상이 실제 실행됐고 어떤 상태·측정값을 돌려줬는가</td></tr></tbody></table><h2>함께 읽기</h2><p><ac:link><ri:page ri:content-title="04. 실행 준비와 설정 관리"/><ac:plain-text-link-body><![CDATA[04. 실행 준비와 설정 관리]]></ac:plain-text-link-body></ac:link> · <ac:link><ri:page ri:content-title="05.
