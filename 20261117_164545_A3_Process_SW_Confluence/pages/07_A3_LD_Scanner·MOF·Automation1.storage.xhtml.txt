<h2>MOF를 이해하는 출발점</h2>
<p>MOF는 기판을 멈추지 않고 이동 중 가공하는 방식이다. Stage가 기판을 움직이고 Scanner가 그 이동을 따라가며 필요한 위치에서 레이저를 조사한다. SW는 설계점뿐 아니라 Stage 진행 방향·Encoder scale·대기 threshold·Head 축 변환과 레이저 조건을 같은 회차에 묶어 전달해야 한다.</p>
<p>PC가 모든 가공점의 순간을 화면 갱신 주기로 직접 맞추는 것으로 이해하면 잘못된 튜닝을 하게 된다. PC는 계획·Script·실행 요청·상태와 결과를 관리하고, 실제 생성 명령의 시간·좌표 동작은 Controller와 Stage Encoder 관계에 의존한다. 다만 이 구조 설명만으로 Controller 성능과 광학 정밀도가 보장되는 것은 아니다.</p>
<h2>Head·Controller·Task·Encoder는 다른 대상</h2>
<table><tbody><tr><th>대상</th><th>역할</th><th>확인값</th></tr><tr><td>HeadNo</td><td>물리·논리 가공 Head 구분</td><td>활성 여부, 배정 Shot 수와 광학 구성</td></tr><tr><td>AutomationNo</td><td>어느 Automation1 통신 대상으로 보낼지</td><td>Interface 등록과 실제 연결 대상</td></tr><tr><td>TaskNo</td><td>Controller 안의 실행 단위</td><td>파일·상태·Fault·Ready 변수 인덱스</td></tr><tr><td>GX/GY 축</td><td>Scanner의 명령·피드백 축</td><td>설정된 축 이름·swap/flip·이동 제한</td></tr><tr><td>Encoder 축·AUX</td><td>Stage 이동량을 읽는 기준</td><td>실제 입력 축·count/mm·극성·zero 시점</td></tr></tbody></table>
<p>TaskNo 기본값이 HeadNo여도 매핑을 따로 읽는다. 통신 대상0, Head1, Task1 같은 숫자는 각각 다른 namespace에 속한다. 특히 zero 대상의 Encoder 축을 잘못 고르면 Script 파일과 가공점이 맞아도 follow 기준이 달라진다.</p>
<h2>한 회차의 생성물과 실행 증거</h2>
<table><tbody><tr><th>산출물·식별자</th><th>설명</th><th>분석 시 역할</th></tr><tr><td>ST_PROCESS_MODEL</td><td>Recipe·Glass·Lot·조건과 HeadPlan의 사본</td><td>실행 입력을 동결한 기준</td></tr><tr><td>PROCESS_Hxx.ascript</td><td>Head별 명령 파일</td><td>어느 축·대기점·Laser 조건인지 확인</td></tr><tr><td>PROCESS_COORDINATES.csv</td><td>회차 좌표와 Offset 성분 추적</td><td>화면·모델·Script의 숫자 대조</td></tr><tr><td>PROCESS.txt·Manifest</td><td>이번 생성파일과 Head별 경로 묶음</td><td>업로드할 정확한 FilePath 확인</td></tr><tr><td>MofReadyRunId</td><td>이번 빌드의 준비 신호 식별자</td><td>과거 Task의 Ready와 현재 Ready 구분</td></tr></tbody></table>
<p>Station은 생성 결과의 HeadScripts를 순회하며 점 수가 있는 Head의 Manifest FilePath를 업로드한다. 이름이 같은 예전 파일을 임의 최신 경로에서 다시 찾는 설명을 넣지 않는다. 파일 생성 성공, 업로드 성공, Task 시작, MOF 준비, 완료는 서로 다른 증거다.</p>
<h2>현재 Main의 일반 실행과 Buffered 실행</h2>
<table><tbody><tr><th>구분</th><th>일반 RUN</th><th>Buffered RUN</th></tr><tr><td>명령 공급</td><td>Controller 파일 Compile 후 Program.Run</td><td>Command Queue에 Controller 파일의 명령을 공급</td></tr><tr><td>핵심 호출</td><td>Files.Upload → Compiler.CompileControllerFile → Task.Program.Run</td><td>BeginCommandQueue → ExecuteFromControllerFile → 완료 대기</td></tr><tr><td>소스 구조</td><td>일반 Script는 program 블록을 생성하는 분기</td><td>Buffered는 그 분기를 사용하지 않음</td></tr><tr><td>상태 확인</td><td>Task의 실행·완료·Fault를 확인</td><td>Queue 공급·실행·Task 상태와 정리를 확인</td></tr><tr><td>오류 후 처리</td><td>Station 실패·Stop·Task 상태를 추적</td><td>Stop 요청과 finally Queue 종료·cleanup을 추적</td></tr></tbody></table>
<p>일반 RUN의 현재 구현은 CompileControllerFile(...compileWithDebugInformation:true) 다음 Program.Run을 호출한다. Buffered는 BeginCommandQueue(...shouldBlockIfFull:false)로 시작하고 ExecuteFromControllerFile(file,linesPerCommand)를 호출한다. 소스에 두 경로가 있으므로 “A3는 Compile을 쓰지 않는다”라고 일반화하지 않는다.</p>
<p>8월 MOF WPF 샘플의 별도 Buffered 안내에는 shouldBlockIfFull:true와 WaitForEmpty 절차가 적혀 있다. 같은 과거 통합 가이드에는 Compile·Source 보호 설명도 있다. 과거 문서의 모드·개정 차이를 최신 Main의 불변 API 계약으로 복사하지 않는다. 특히 Script가 항상 암호화 저장되거나 Debug 정보가 제거된다고 이 페이지에서 보장하지 않는다.</p>
<h2>현재 Buffered 준비파일의 소유권</h2>
<p>RunBufferedScripts는 업로드를 포함하는 경로이고 RunStagePreparedBufferedScripts는 upload:false, stageSession:true다. 후자는 DoReady에서 이미 업로드한 정확한 Controller 파일을 실행하며 LocalScriptPath는 사용하지 않는다는 주석이 있다. PC 원본을 실행 직전에 바꾸더라도 준비된 Controller 파일이 자동 교체되는 것은 아니다.</p>
<ol><li>회차별로 생성된 Head 파일·Task 목록과 매핑을 검증한다.</li><li>해당 파일을 준비 단계에서 업로드하고 각 응답을 확인한다.</li><li>준비 세션이 소유한 파일과 Task·Queue 목록으로 실행한다.</li><li>공급 함수가 반환된 뒤에도 완료 대기를 수행한다.</li><li>예외·취소 시 대상 Task 정지와 Queue cleanup이 끝났는지 확인한 뒤 다음 실행에 소유권을 넘긴다.</li></ol>
<p>동일 Controller에서 Task 번호가 중복된 Buffered 요청은 거부하는 경로가 있다. 중복 클릭이나 재시도 때 새 Task를 덮어 실행하는 방식으로 회피하지 않고, 이전 worker와 cleanup의 상태를 확인한다.</p>
<h2>MOF Ready가 게시되는 위치</h2>
<p>Script는 Task별 GlobalInteger 인덱스와 RunId를 기록한다. 시작 시 준비값을0으로 내리고 단위·속도·Ramp·Laser 조건을 구성한다. Scanner X/Y를 중심으로 이동하고, 실기 분기에서는 AUX feedback zero와 Encoder scale 설정을 수행한다. 이후 MotionDone을 기다린 뒤 이번 RunId를 게시하고 follow 진입을 이어간다.</p>
<pre><code>준비값 0 → Scanner 중심화 → AUX 기준·scale 설정
→ WaitForMotionDone → GlobalInteger = 이번 RunId
→ Stage Encoder 이동을 따라가는 follow·가공</code></pre>
<p>Ready를 follow 호출 뒤로 무조건 옮기면 Stage 움직임을 기다리는 명령 때문에 준비 게시가 막힐 수 있다는 주석이 있다. 반대로 PC의 Run 요청 반환을 Ready로 대신하면 초기화·중심화가 끝나지 않은 상태를 넘길 수 있다. 준비 신호에는 현재 회차를 구별할 RunId와 실제 검사 위치가 함께 필요하다.</p>
<p>최신 AUTO에서는 DoReady가 업로드만 맡고 MOF zero/Task RUN은 DoReady 신호 reset 뒤 Process 준비로 분리되어 있다. 단순히 DoReady COMPLETE가 보였다는 이유로 레이저 조사까지 끝났다고 해석하지 않는다. 신호의 이름과 의미, 실제 코드에서 언제 쓰는지를 함께 기록한다.</p>
<h2>명령과 상태 조회를 나누는 동시성</h2>
<p>CAutomation1Comm의 lock 순서는 _commLock→_statusReadLock다. Buffered feed는 _commLock만 유지하고 읽기 전용 상태 lane은 _statusReadLock을 사용하며 _commLock을 기다리지 않는다. 일반 명령·Connect/Disconnect와 긴 Buffered 실행이 경합할 수 있으므로, 상태 조회를 빨리 보이게 하려고 반대 순서의 잠금을 새로 넣으면 교착을 만들 수 있다.</p>
<p>Task Fault와 통신 Offline도 구분한다. SDK의 명령 오류를 연결 끊김으로 바꿀지, 실제 연결 예외를 어떻게 표출할지는 Comm의 예외 경계를 따른다. UI에서는 대상 AutomationNo·TaskNo·마지막 정상 취득시각·상태와 명령 오류를 함께 확인할 수 있어야 한다.</p>
<h2>속도·Queue 조건을 평가할 때</h2>
<p>linesPerCommand는 파일을 몇 행씩 공급하는지, queueSize는 명령 대기 용량, timeout은 대기 한도와 관련된다. 가공점 수·Stage 속도·Jump/Mark 속도와 같은 물리 변수와 구분한다. 줄 수를 늘렸다는 사실만으로 정착·정밀도·최대 Stage 속도가 개선되었다고 결론내리지 않는다.</p>
<p>평가에서는 같은 입력과 파일을 고정한 뒤 공급량, 실행 완료시간, Queue 고갈·Fault·Stop, 축 추종과 실제 가공 품질을 각각 관측한다. 최종 정상 drain과 중간 공급 부족도 구분한다. 아직 시험하지 않은 속도를 도구 계산값만으로 양산 가능한 값으로 표시하지 않는다.</p>

<h2>검증 범위와 다음 확인</h2>
<p>Interface Simulation의 합성 OK, Motion Simulation과 AUTOMATION1_SIMULATOR_USE의 Script 분기는 서로 다른 조건이다. Simulation이 통과했다는 사실만으로 실제 Controller compile·AUX 입력·레이저 출력·Queue 연동을 통과했다고 보고하지 않는다. Controller가 Online이어도 Task Fault와 물리 출력 상태는 별도로 확인한다.</p>
<p>후속 검증은 같은 ProcessModel의 일반/Buffered 생성물 비교, 중복 Task, 이전 Ready 잔류, 취소·통신 단절·Queue cleanup, Simulator/실기 좌표 분기부터 나눈다. 이후 승인된 현장 절차로 Encoder 방향·Dry Run·실가공을 확인한다. 이번 페이지 작성 중 장치 호출·Script 실행·새 성능계측은 수행하지 않았다.</p>
