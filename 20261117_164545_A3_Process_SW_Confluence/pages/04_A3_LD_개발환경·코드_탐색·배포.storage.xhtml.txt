<h2>2. 개발환경 확인</h2>
<p>UI는 <code>net8.0-windows</code> WPF, Common과 File은 <code>net8.0</code> 프로젝트다. Windows의 .NET 8 SDK와 WPF 개발 도구를 준비하고, 저장소에 포함된 <code>NuGet.config</code> 및 실제 참조 DLL 경로를 확인한다. Visual Studio에서 작업한다면 .NET 데스크톱 개발 환경과 .NET 8 SDK가 필요하다. 이 문서 작업에서는 정식 설비 빌드를 실행하지 않았다.</p>

<h2>3. 처음 확인할 명령</h2>
<p>아래 명령은 <code>Drilling.sln</code>이 있는 본인의 개발 작업사본에서 실행하는 예다. 현재 작업물과 브랜치가 올바른지 확인한 뒤 사용한다. 장비 실행이나 Laser 출력 명령은 포함하지 않는다.</p>
<pre><code>git status --short
git branch --show-current
git rev-parse HEAD
dotnet --info
dotnet restore ./Drilling.sln
dotnet build ./Drilling.sln -c Debug --no-restore</code></pre>
<p>Restore/Build 결과는 실제 수행한 PC·SDK·Commit·오류 원문과 함께 저장한다. 과거의 특정 오류 개수나 문서용 부분 컴파일 진단 수를 이번 빌드 결과로 옮기지 않는다. Build 성공도 벤더 DLL 로드, Controller 컴파일, PLC·Vision 통신, 실제 가공 성공을 의미하지 않는다.</p>
<h2>4. Config와 Data 경로를 먼저 찾는 이유</h2>
<p><code>CAppStartup.GetConfigRoot</code>는 실행파일의 BaseDirectory에서 위로 올라가며 <code>Drilling.sln</code>을 찾으면 그 위치의 <code>Config</code>를 선택한다. 찾지 못하면 현재 작업 디렉터리의 <code>Config</code>를 사용한다. 따라서 개발 실행과 독립 배포 실행은 같은 파일을 읽는지 반드시 시작 로그로 확인한다.</p>
<p>Script 경로는 Setting의 <code>LocalScriptPath</code>를 읽으며 비어 있으면 <code>Data/Script</code>를 사용한다. 상대 경로는 Config의 부모인 프로젝트 루트에 맞춰 해석한다. 이름이 비슷한 Config 사본을 수정하는 대신 ProgramOpen의 실제 <code>ConfigRoot</code>, 초기화 순서와 로드 건수를 대조한다. 작업 중인 Recipe, 활성 보정, Product 상태와 Log의 실제 경로도 함께 기록한다.</p>
