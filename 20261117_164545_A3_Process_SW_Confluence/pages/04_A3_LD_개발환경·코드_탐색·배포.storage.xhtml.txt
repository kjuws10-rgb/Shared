<h2>1. 어떤 프로그램과 버전인가</h2>
<p>이 문서의 현재 Main SW 기준은 <code>Ver11.17.0</code>이다. <code>Drilling.UI.csproj</code>의 Version은 <code>2026.11.13.0</code>이다. 개발 기준과 실행파일의 Version 표기가 다르므로 인수인계 기록에는 두 값을 함께 남긴다. 실행파일 속성만으로 모든 변경을 식별하지 않는다.</p>
<p>이전 구조 분석 이후 기존 C#/XAML/프로젝트 파일의 수정 없이 신규 코드 4개가 추가됐고 설정·운영 데이터도 변경됐다. 신규 Review 지도·색상 클래스는 <ac:link><ri:page ri:content-title="11. A3 LD 운전 화면과 Manual·Auto"/><ac:plain-text-link-body><![CDATA[운전 화면]]></ac:plain-text-link-body></ac:link>에서 계산 로직과 실제 화면 연결 여부를 구분해 설명한다. 코드 설명이 같아도 장비 적용 설정까지 같다고 확대하지 않는다.</p>

<h2>2. 개발환경 확인</h2>
<p>UI는 <code>net8.0-windows</code> WPF, Common과 File은 <code>net8.0</code> 프로젝트다. Windows의 .NET 8 SDK와 WPF 개발 도구를 준비하고, 저장소에 포함된 <code>NuGet.config</code> 및 실제 참조 DLL 경로를 확인한다. Visual Studio에서 작업한다면 .NET 데스크톱 개발 환경과 .NET 8 SDK가 필요하다. 이 문서 작업에서는 정식 설비 빌드를 실행하지 않았다.</p>

<h2>3. 처음 확인할 명령</h2>
<p>아래 명령은 <code>Drilling.sln</code>이 있는 본인의 개발 작업사본에서 실행하는 예다. 현재 작업물과 브랜치가 올바른지 확인한 뒤 사용한다. 장비 실행이나 Laser 출력 명령은 포함하지 않는다.</p>
<pre><code>git status --short
git branch --show-current
git rev-parse HEAD
dotnet --info
dotnet restore ./Drilling.sln
dotnet build ./Drilling.sln -c Debug --no-restore</code></pre>
<p>Restore/Build 결과는 실제 수행한 PC·SDK·Commit·오류 원문과 함께 저장한다. 과거의 특정 오류 개수나 문서용 부분 컴파일 진단 수를 이번 빌드 결과로 옮기지 않는다. Build 성공도 벤더 DLL 로드, Controller 컴파일, PLC·Vision 통신, 실제 가공 성공을 의미하지 않는다.</p>
<h2>4. Config와 Data 경로를 먼저 찾는 이유</h2>
<p><code>CAppStartup.GetConfigRoot</code>는 실행파일의 BaseDirectory에서 위로 올라가며 <code>Drilling.sln</code>을 찾으면 그 위치의 <code>Config</code>를 선택한다. 찾지 못하면 현재 작업 디렉터리의 <code>Config</code>를 사용한다. 따라서 개발 실행과 독립 배포 실행은 같은 파일을 읽는지 반드시 시작 로그로 확인한다.</p>
<p>Script 경로는 Setting의 <code>LocalScriptPath</code>를 읽으며 비어 있으면 <code>Data/Script</code>를 사용한다. 상대 경로는 Config의 부모인 프로젝트 루트에 맞춰 해석한다. 이름이 비슷한 Config 사본을 수정하는 대신 ProgramOpen의 실제 <code>ConfigRoot</code>, 초기화 순서와 로드 건수를 대조한다. 작업 중인 Recipe, 활성 보정, Product 상태와 Log의 실제 경로도 함께 기록한다.</p>

Simulation을 통과한 결과와 실장비 연동 결과를 구분한다.</li><li>현장 적용은 담당자의 변경 승인과 <ac:link><ri:page ri:content-title="13. <h2>7. Script와 자료의 보호</h2>
<p>8월 자료의 AES-GCM, Preview 비노출, Debug 제외, 임시 Source 삭제는 각 보호수단의 설계·평가 항목으로 읽는다. 현재 Main 전체에 모두 적용됐다고 단정하지 않는다. 특히 정상 실행을 위해 사용되는 평문, 메모리·로그·백업, 키와 접근권한은 별도 확인 대상이다. 암호화가 해독을 절대 불가능하게 한다거나 Debug 제거가 역공학을 막는다는 표현은 사용하지 않는다. 자세한 출처와 문서 정정 기준은 <ac:link><ri:page ri:content-title="16. A3 LD 자료·산출물·변경관리"/><ac:plain-text-link-body><![CDATA[자료·변경관리]]></ac:plain-text-link-body></ac:link>를 따른다.</p><h2>실제 코드로 읽는 처리 흐름</h2><p>실제 시작 코드가 Config와 Script 폴더를 어떻게 결정하는지 보여준다. 함수 이름만 보고 다른 자료로 이동할 필요 없이 아래의 조건과 반환값을 읽을 수 있다.</p><h3>Config 폴더 선택</h3><p><strong>코드 위치명:</strong> <code>CAppStartup.cs</code> · 본문에서 읽는 실제 구현 발췌</p><ac:structured-macro ac:macro-id="ddd4b2dc-451f-50ef-86f2-95d25c4b871b" ac:name="code" ac:schema-version="1"><ac:parameter ac:name="language">csharp</ac:parameter><ac:parameter ac:name="title">Config 폴더 선택</ac:parameter><ac:parameter ac:name="linenumbers">false</ac:parameter><ac:plain-text-body><![CDATA[    private static string GetConfigRoot()
