<h2>1. 이 페이지의 역할과 현재 기준</h2>
<p>이 페이지는 고객이 원하는 기능, 누가 수행할 개발 작업, 코드에서 확인한 기능, 실제 시험 결과를 하나의 추적 체계로 연결한다. 요구사항 수, WBS 수, 코드 파일 수, 체크시트 시험 수는 서로 다른 모집단이므로 합산하거나 하나의 완료율로 나누지 않는다. 신규 담당자는 요구ID에서 코드·시험·미결 계약으로 내려가고 장애에서 영향받는 요구ID로 다시 올라갈 수 있어야 한다.</p>
<p>코드 기준은 A3Drilling master Commit 9a43c709다. Git Commit 메시지는 Ver11.17.0이며 실제 실행파일·배포 Version은 별도로 대조해야 한다. 현재 csproj의 Version은 2026.11.13.0이므로 Commit 메시지와 같은 의미로 쓰지 않는다. 코드 레퍼런스는 dfa5920e 기준으로 제작된 별도 자료이며 그 뒤의 새 코드·설정·데이터와 동일하다고 자동 가정하지 않는다. 이번 담당 범위에서는 Recipe·Interface·Power 관련 주요 기존 파일의 바이트 동일성을 확인했다. 실장비 시험·고객 Acceptance의 현재 완료 여부는 이 자료만으로 확정하지 않는다.</p>

<p>한 요구에 여러 WBS가 연결될 수 있고 한 WBS가 여러 요구를 지원할 수 있다. 따라서 단순 연결 행 수를 기능 수나 완료 수로 세지 않는다. 소스가 바뀌면 그 변경이 영향을 주는 요구·시험만 재확인하고 관계없는 과거 합격을 무조건 현재 버전의 합격으로 승계하지 않는다.</p>
<h2>4. 다섯 요구 영역을 읽는 방법</h2>
<p>AM은 Auto/Monitoring 16개, MM은 Manual 9개, RD는 Recipe 7개, IC는 검사·보정 11개, SS는 설정·통신 8개로 총51개다. AM에서 Glass·알람·CIM·광학·Sequence·모드·JobChange의 운영 흐름을 보고, RD에서 조건과 저장·적용의 정합성을 본다. MM은 단순 조작 버튼 존재보다 선택 Head·상태·한계·실제 완료가 중요하다. IC는 측정 계획·유효 결과·단위·보정 소비·이력으로 내려가고, SS는 장비·프로토콜·교정·환경 설정으로 연결한다.</p>
<p>예를 들어 AM-014 자동 Job Change는 Recipe SELECT 버튼 하나로 완료하지 않는다. Host/Sub 매핑, 수신·적용 시점, 기판 귀속, 측정·보상, 실패 복구와 완료 보고를 <ac:link><ri:page ri:content-title="05. A3 LD PPID·Recipe·OSS·Job Change"/><ac:plain-text-link-body><![CDATA[PPID·OSS·Job Change]]></ac:plain-text-link-body></ac:link>에 연결한다. SS-004 파워보정은 Driver 존재와 실제 장치 세션, 측정·ATT 보정, 저장·정리·AUTO TPM 인계까지 <ac:link><ri:page ri:content-title="10. A3 LD 광학 Component와 Power"/><ac:plain-text-link-body><![CDATA[광학 Component와 Power]]></ac:plain-text-link-body></ac:link>에서 추적한다. 이 예시는 현재 완료 판정이 아니라 추적 범위를 설명한다.</p>
<h2>5. 구현·시험·인수 상태를 판정하는 기준</h2>
<p>요구 문장이 있으면 “요구 확인”, 계약이 정해졌으면 “사양 합의”, 해당 코드 분기가 있으면 “구현 근거 확인”, 격리 시험을 실행했으면 “시험 결과 확보”, 실제 장치 연계와 고객 기준을 만족했으면 그 범위의 인수 판정을 기록한다. 이 표현들은 관리 기준 제안이며 현재 모든 항목이 이 단계를 밟았다고 뜻하지 않는다. 상태를 붙일 때는 구체적인 증거를 함께 적는다.</p>
<p>미확인은 실패와 다르다. 시험을 수행하지 않았으면 미실행/미확인이고, 실행해 기대와 달랐으면 실패 결과와 재현조건을 남긴다. 코드에는 있으나 승인 기준이 없으면 사양 미결을 별도로 표시한다. N/A는 적용하지 않는 근거와 승인 범위를 남겨야 하며 빈칸을 N/A로 처리하지 않는다. 안전·인터락·실제 광학 정밀도 합격은 문서 UI 검수와 따로 판정한다.</p>
<h2>6. 통합시험 묶음과 증거</h2>
<p>제조 체크시트 R0는 HW/IO189, 기능217, 알람324, SW 인터락66, 외부 연동109, 연동 제한31, AUTO35로971항목을 작성한 자료다. 결과·검사일·서명·Issue 처리결과는 공란이며 초기 진행률0%다. 이 수량은 작성 당시 코드·맵의 커버리지이고 현 최신 버전에서 같은 개수의 시험을 끝냈다는 뜻이 아니다. 개정 전에는 현재 설정과 비교해 추가·삭제·변경된 항목을 먼저 검토한다.</p>
<ol><li>단위·데이터: 파싱, 좌표계·배율, 경계값·미수신·0·중복, Recipe 저장/재로드를 평가한다.</li><li>통신: 연결·명령·ACK·완료, Timeout·중복·단절·stale 캐시·재기동을 평가한다.</li><li>시퀀스: 준비·가공·Review·0선·TPM·Distortion의 신호 소유권과 정리, 모드별 실행 범위를 평가한다.</li><li>정합성과 복구: Glass/Run/Recipe 귀속, 결과·보정·Product·보고의 저장 경계, 부분 실패와 원복을 평가한다.</li><li>현장 물리 검수: 실제 Stage/광학 구성·센서·정밀도·출력·인터락·정지/재개를 승인 조건에 따라 평가한다.</li></ol>
<p>각 묶음의 합성·Simulation 결과와 실장치 결과를 구분한다. 문서의 정적 assertion 수, HTML 조작 테스트 수, Roslyn 진단 수를 장비 시험 수·설비 빌드 오류·합격률로 바꾸지 않는다.</p>
<h2>7. 현재 우선 확인할 미결과 변경</h2>
<p>11/17 OSS 검토의 핵심은 Host/SubPPID 연결, Distortion 필수 조건·좌표·Step/Direction, Center Pin의 PLC 관리, JobChange 완료 시점, 결과·실적과 동적 I/F 분리, 단위·타입·문자열·Mask/Cell/Model 정합성이다. 이는 문서 누락·협의 항목이며 곧바로 생산 SW 결함 개수로 세지 않는다.</p>
<p>최신 코드 검토에서는 Review EDIT의 출처와 보정 후보, Revision 계보의 재누적 가능성, Product 재시작 복구의 NG 메타데이터, ONE_LINE 측정과 Offset 적용 범위, 보호윈도우 재시도 소진·복구를 확인할 필요가 있다. 과거 PowerMeasure Simulation만 존재한다는 설명은 현재 DeviceSession·Manual/AUTO 통합 코드와 대조해 정정해야 한다. 현재 코드 존재와 실기 결과가 확인됐는지의 두 질문을 따로 유지한다.</p>
<h2>8. 주간 변경과 인수인계 운영</h2>
<ol><li>기준 Commit·장비 설정·사양 개정을 먼저 고정하고 지난 기준과 변경 목록을 확인한다.</li><li>변경을 요구ID와 WBS, 관련 데이터·통신·화면·시퀀스·시험에 연결한다.</li><li>새 근거가 있는 항목만 판정하고 나머지 상태는 유지한다. 담당·일정은 실제 합의된 값만 쓴다.</li><li>열린 계약·실패 Issue·실기 미실행 항목을 다음 행동과 선행조건으로 정리한다.</li><li>인수 시 요구별 구현·시험·현장·승인 근거와 알려진 제한, 재현·복구 방법을 함께 넘긴다.</li></ol>
<p>이 체계의 완료 조건은 표가 빈칸 없이 채워지는 것이 아니라 다음 담당자가 같은 조건에서 근거를 찾고 판정을 재현할 수 있는 것이다. 확인하지 않은 고객 승인·실제 완료일·장비 결과를 추정으로 채우지 않는다.</p>
