<h2>1. 자료를 찾는 우선순위</h2>
<p>현재 구현을 묻는 질문은 적용 Commit의 실제 코드·정의 파일에서 시작한다. 회의와 요구서는 의도와 완료조건을 설명하고, 시험 기록은 특정 환경에서 실제 확인한 결과를 설명한다. 본문의 설명 그림과 코드 발췌, 별도 시뮬레이터는 이해를 돕는 자료다. 같은 기능 이름이어도 각 자료가 증명하는 범위를 함께 읽는다.</p>

<h2>3. 이번 종합에서 실제 확인한 범위</h2>
<p>프로젝트 지식 작업실의 전체 카테고리 색인, PRJ-A3의 상태·결정·산출물·관련 작업기록, 접근 가능한 과거 대화의 선택된 최근 턴, 등록된 8월 문서 원문, Shared 설명자료와 Main 실제 소스를 대조했다. 최신 원격 Commit과 별도 읽기용 소스 사본도 확인했다. 코드 레퍼런스의 전체 파일 색인을 검토한 것과 원문 모든 줄을 의미 분석한 것은 다르다.</p>
<p>사내 Confluence 본문은 현재 환경에서 직접 읽지 못했으므로 사용자가 붙여준 원문과 확보한 동일 계열 문서를 사용했다. 모든 과거 채팅의 모든 턴·삭제된 첨부·사내 문서를 확보한 것은 아니다. 임시 첨부 위치가 보이더라도 파일을 실제 열지 못한 경우에는 본문 확인으로 표시하지 않았다. 확인한 범위와 미확보 자료는 이 절의 설명을 기준으로 구분한다. 실제 구현의 핵심 코드는 각 주제 페이지 본문에서 확인한다.</p>

<p>GCM의 목적과 조건은 <a href="https://csrc.nist.gov/pubs/sp/800/38/d/final">NIST SP800-38D</a>를 따른다. 특정 프로그램에 적용됐는지는 실제 암호화·키 관리·nonce 생성·복호화·저장·삭제 코드와 시험 근거로 따로 확인한다.</p>

<h2>6. 페이지와 첨부파일을 관리하는 방법</h2>
<ol><li>상위 페이지 제목은 <strong>Process SW 개발</strong>로 만들고, 배포 순서표의 제목과 같은 이름으로 하위 페이지를 만든다.</li><li>각 페이지의 독립 <code>.storage.xhtml.txt</code> 내용 전체를 소스 편집기에 붙여넣는다. 일반 본문 편집기에 코드 자체를 붙여넣는 방식과 구별한다.</li><li>그림이 있는 페이지에는 해당 페이지에 지정된 PNG 첨부파일을 동일한 이름으로 업로드한다. 원본 SVG는 수정용으로 함께 보관한다.</li><li>다른 페이지 링크는 같은 Space의 정확한 제목을 참조한다. 제목을 변경하면 링크와 순서표도 함께 점검한다.</li><li>자료명·버전·파일·함수·행과 확인 범위는 일반 텍스트로 기록하고 필요한 설명은 해당 페이지 본문에 담는다. 존재가 확인되지 않은 과거 첨부파일의 링크는 새로 만들지 않으며 고객/사내 원문은 정해진 보관 범위에 둔다.</li><li>저장 후 TOC·표·코드·페이지 링크·이미지·출처를 확인한다. 이번 로컬 XML/미리보기 검증은 사내 Confluence 렌더링 검증과 별도다.</li></ol>
<p>Confluence의 링크·첨부 식별자는 <a href="https://confluence.atlassian.com/doc/confluence-storage-format-790796544.html">Atlassian Storage Format</a>을 참고했다. 이 묶음은 사용자 제공 소스 형식에 맞췄으며 사내 설치본에서의 최종 저장·권한·매크로 동작은 붙여넣은 뒤 확인해야 한다.</p>
