<h2>1. 검사와 보정의 전체 흐름</h2>
<p>검사는 현재 가공 결과가 목표에서 얼마나 벗어났는지 알아내는 일이고, 보정은 그 오차를 다음 가공 명령에 반영하는 일이다. A3 LD에서는 <strong>검사 계획 → 이동·Trigger 준비 → Vision 측정 → 좌표·판정 변환 → 결과 저장 → 보정 후보 계산 → 보정 파일 저장 → 다음 가공 준비에서 읽기</strong>로 나누어 이해한다. 측정 완료, 파일 저장, 품질 OK, 보정 적용은 각각 확인해야 하는 별도 상태다.</p>
<p>이 페이지의 현행 설명은 A3Drilling 9a43c709의 정적 코드와 그 부모 dfa5920e의 상세 해설을 기준으로 한다. 실제 PLC·Vision의 주소, 극성, 분해능과 품질 합격은 배포 사양 및 현장 시험으로 확인해야 한다. 교육용 Review HTML의 조작이 생산 WPF에서 동일하게 제공된다고 가정하지 않는다.</p>

<p>Fine 계산에서 같은 열에 측정점이 하나이면 그 열에 일정 보정량을 사용하고 여러 anchor이면 Y방향 계산을 수행한다. 측정하지 않은 다른 열을 임의의 0으로 채우거나 이웃 Head의 오차로 메우는 정책으로 확대하지 않는다. 실제 외삽·overshoot의 허용 여부는 공정 검증 항목이다.</p>
<h2>4. Vision 오차가 품질 판정으로 바뀌는 과정</h2>
<p>현재 1000/1003/1010 응답 해석에서 nResult=0은 표적 찾기 성공을 뜻한다. raw 오차는 다음과 같다. 이 식에 Head 방향이나 Flip을 미리 한 번 더 곱하면 중복 변환할 수 있다.</p>
<pre>RawErrorX_mm = CameraResolution_mm_per_pixel × nResolution × (TargetMarkX − HoleX)
RawErrorY_mm = CameraResolution_mm_per_pixel × nResolution × (TargetMarkY − HoleY)
Converted = VisionErrorToStageOffset(RawError, VisionFlip)
OK = Found AND abs(ConvertedX) ≤ ToleranceX AND abs(ConvertedY) ≤ ToleranceY</pre>
<p>설명용으로 CameraResolution=0.001 mm/pixel, nResolution=2, Target−Hole=(3,−2) pixel이면 raw 오차는 (0.006,−0.004) mm다. 이 숫자는 장비 설정값이 아니다. <code>VisionPixelsToMillimeters</code>는 분해능·입력·환산값의 유효성을 검사하고, <code>ApplyMeasurementError</code>는 Flip 후 각축 허용오차로 판정한다. 현재 구현에서 허용오차 경계와 정확히 같은 값은 초과가 아니므로 정상 찾기 조건에서는 OK다.</p>
<p>1001 Flying Ready의 한 점은 Cell, Doe, Line, IndexX, IndexY, Head의 정수 6개다. mm X/Y 배열이 아니며, 실제 Stage IOF 위치 배열은 별도 경로다. 실패 시도와 재시도의 Trigger buffer 순서가 달라질 수 있으므로 1003 결과는 해당 시도의 동결된 버퍼와 매칭한다.</p>
<h2>5. Align·Distortion, Default, First, Review를 분리한다</h2>
<table><tbody><tr><th>보정</th><th>현재 의미와 수명</th><th>잘못 합치기 쉬운 지점</th></tr>
<tr><td>Align / Distortion</td><td>현재 Glass의 Base−LastLoad로 설계 좌표 보정을 계산하고 다음 DoReady에 연결한다.</td><td>장기간 누적 Review Offset 파일과 다른 수명이다. 결과 수신 후 기존 Script를 그대로 쓰지 않는다.</td></tr>
<tr><td>Default</td><td>Head 기준을 맞추는 Recipe 기본 보정이다.</td><td>조건창의 AK1·AK3 X평균은 입력 평균이다. 새 촬영이나 2D 회전 정합 완료로 해석하지 않는다.</td></tr>
<tr><td>First Beam / First Offset</td><td>기준에서 실제 가공 첫 빔 위치로 대응시키는 별도 성분이다.</td><td>원빔의 DOE 11번 대응 위치 문제를 Default 자체의 정의와 섞지 않는다.</td></tr>
<tr><td>Review Offset</td><td>기존 Design 보정값에 이번 Delta를 더해 새 snapshot으로 저장한다.</td><td>지금 저장한 값이 이미 생성된 현재 Glass 명령을 소급 수정하지 않는다.</td></tr></tbody></table>
<p>현재 Distortion은 AK1~4와 선택한 DK 그룹을 사용한다. DK 그룹 0~2는 각각 두 점이므로 최대 AK4+DK6=10점이다. 옛 자료의 “6개”가 DK만을 뜻하는지 전체를 뜻하는지 확인한 뒤 비교한다. AK4 글로벌값을 현재 map에서 읽는 수동 Load와, 새 측정을 요청해 현재 Glass 결과를 얻는 동작도 구분한다.</p>
<p>현재 Default의 SPLITED_BEAM_COUNT 허용값 1/4는 격자 한 변의 수이며 실제 검사 슬롯은 1/16개다. 모든 Head에 같은 전역값을 쓰는 코드이므로 DOE 장착 3 Head와 원빔 5 Head의 혼합 지원으로 확대하지 않는다. DOE 없는 원빔은 실제 Zero Order 출사 위치를 뜻하며 전역 좌표 (0,0)이나 16개 중 하나의 선택을 뜻하지 않는다.</p>
<h2>6. 일반 AUTO Fine 결과를 확인하는 순서</h2>
<ol><li>실행 전 Glass·Recipe·Run, 선택 Head·Cell·Beam, 검사 줄·점 수와 Masking 제외 결과를 보관한다.</li><li>Prepare 시점 계획과 실제 Stage 버퍼, Vision 검색 식별자가 같은 점 집합인지 확인한다.</li><li>정상 완료, 결과 파일 경로, ResultSaveError 없음, 대상과 결과 식별자·개수 일치를 확인한다.</li><li>찾기 NG와 tolerance NG를 구분한다. 하나라도 NG이면 기존 Review Offset 전체를 유지하는 AUTO 정책을 확인한다.</li><li>일반 AUTO인지 0선 Follow-up인지 확인한다. 후자는 검사만 수행한다.</li><li>일반 AUTO의 Current/Delta/Final, 기존·새 Offset 파일과 적용 이력을 확인한다. 저장값은 기존값을 Design으로 바꾼 뒤 Delta를 더한 값이다.</li><li>다음 가공 준비에서 새 Offset 파일이 실제로 읽혔는지 준비 snapshot과 최종 Script를 대조한다.</li></ol>
<p>UI의 COPY/KEY IN → RESULT SAVE → OFFSET APPLY는 서로 다른 단계다. COPY는 결과 후보를 편집하며 새 EDIT Revision을 만든다. 출처 열이 있는 파일은 MEASURED만 적용하고, 출처가 없는 ONE SHOT/Legacy는 OK/NG 행으로 fallback하는 현재 경계가 있다. 따라서 편집 결과가 항상 보정에 들어가거나 항상 제외된다고 설명하지 않는다.</p>
<h2>7. 즉시 대응할 때 확인할 제한</h2>
<ul><li>BASE→부분 EDIT/REINSP→다시 Apply는 같은 측정 계보의 Delta 재누적 위험을 별도로 확인한다. 현재 중복 이력은 날짜와 정규화한 경로에 의존한다.</li><li>결과 CSV의 optional 숫자 파싱은 누락·비정상 입력을 0으로 보이게 할 수 있다. 화면의 0만으로 실제 무오차 측정이라고 판단하지 않는다.</li><li>Offset Rollback은 최신 활성 snapshot 한 단계 원복이다. 결과 Revision, 판정, Default, 모든 Recipe를 함께 되돌리는 기능이 아니다.</li><li>Masking의 점 제외와 Stage의 물리 경로 회피는 별도다. 설계 footprint→Sampling→최종 버퍼→실제 Trigger를 차례로 본다.</li></ul>

]]></ac:plain-text-body></ac:structured-macro><p><strong>읽는 방법:</strong> 입력 문자열을 공백 제거·대문자로 정규화하고 보정 적용을 지원하는 결과 종류인지 반환한다. 목록에 ONE_LINE이 없으므로 단일 줄을 검사·저장할 수 있다는 사실과 그 결과의 Offset Apply 지원을 구분한다. 결과 파일이 존재한다는 이유만으로 종류 검사를 건너뛰지 않는다.</p>
