<h2>1. 광학 제어와 Power 보정의 목적</h2>
<p>광학 장치는 레이저를 켜는 버튼의 집합이 아니다. Laser는 출사 상태와 조건, ATT는 감쇠 위치, BEX는 광학 배율·발산 관련 렌즈 위치, DOE와 원빔은 실제 빔 구성, PowerMeter는 측정된 출력, Scanner는 조사 위치와 실행 경로를 담당한다. 각 장치의 제어값과 물리 결과를 같은 숫자로 취급하지 않는 것이 출발점이다.</p>
<p>코드 기준은 A3Drilling Commit 9a43c709다. Git Commit 메시지는 Ver11.17.0이며 실제 실행파일·배포 Version은 별도로 대조해야 한다. 이 페이지는 현재 Driver·PowerMeasureRun·Service를 직접 읽은 설명이다. 과거 2026-08의 독립 WPF 검증 예제와 10월 문서의 “신규 측정은 Simulation” 설명을 현재 통합 상태로 그대로 사용하지 않는다. 현재에는 실제 장치 세션을 사용하는 Manual/AUTO 공유 코드가 있으며, 그것이 현장 광출력·정밀도 검수 합격을 뜻하지는 않는다.</p>

<h2>3. Power 데이터의 구분</h2>
<p>목표 출력 W, 실제 측정 W, ATT 각도, 센서 식별자, 파장 조건, 측정 횟수·간격, 허용오차, 최대 시도, 안정화·냉각 시간은 각각 다른 값이다. 제품 조건·장비 교정·실행 실적 중 어디에 속하는지 정하고 출처를 기록한다. 코드가 Setting에서 목표값을 읽는 경로와 향후 PPID별 목표 관리 제안을 혼동하지 않는다.</p>
<p>실측 Table은 Head·ATT 각도·측정 출력을 연결해 시작 각도와 보정에 사용된다. Simulation 기록은 별도의 writable store로 구분하며 실제 교정표를 오염시키지 않는다. 측정 보고에는 Recipe, Origin(AUTO/MANUAL), 시작·종료시각, Head 결과와 Simulation 여부가 포함되는 구조다. 가상 출력으로 OK가 나와도 실제 광학 검수 OK로 집계하지 않는다.</p>
<h2>4. 현재 공유 PowerMeasure 실행 흐름</h2>
<p>CPowerMeasureRun은 Manual과 AUTO가 공유하는 준비→측정→정상 결과 저장→정리 거래다. 내부 CPowerMeasureDeviceSession은 실제 Interface와 Automation/MELSEC를 사용한다. 별도 CPowerMeasureSimulationSession도 있으므로 클래스를 찾았다는 이유만으로 실행이 전부 가상 또는 전부 실장비라고 단정하지 말고 실제 주입된 세션·장치별 Simulation 플래그를 확인한다.</p>
<ol><li><strong>대상 검증:</strong> Head와 전용 센서의 중복·범위, 양수 목표 W, 측정 옵션·허용오차·최대 시도를 확인한다. 현재 경로는 Head 1~8과 PowerMeter 번호 Head-1의 대응을 검사한다.</li><li><strong>Stage 확인:</strong> Stage Y 위치와 Busy 맵, 동일 MELSEC 장치, 유효한 새 Snapshot을 확인한다. 현재 코드에는 Y=0 부근·Busy=0·fresh 조건이 있으며 Run 자체가 Stage Y를 이동시키지는 않는다.</li><li><strong>전체 경로 준비:</strong> 사용 Head, Scanner X/Y와 Automation Task, 센서·ATT 연결, Task 상태, ATT 현재 위치와 Laser 상태를 먼저 검사한다. Head 간 Task/축 중복도 차단한다.</li><li><strong>측정 준비:</strong> Scanner CENTER 조건과 주파수 등을 준비하고 측정 가능한 상태를 확인한다. 준비 실패를 건너뛰어 일부 Head만 출사시키지 않는다.</li><li><strong>측정·ATT 보정:</strong> 안정화 뒤 정한 횟수만큼 W를 읽고 목표와 허용오차를 비교한다. 필요하면 출력을 정리한 뒤 ATT를 이동하고 실제 위치를 확인해 다시 측정한다.</li><li><strong>Recipe ATT 각도 저장:</strong> 모든 대상 Head가 OK인 결과에만 SavePowerMeasureAngles를 통해 대상 Recipe의 해당 Head ATT 각도를 저장한다. 이 조건은 Recipe 각도 저장 Gate의 범위다. 측정 Table 실적과 NG 보고는 실패 과정에서도 별도로 기록될 수 있다. 결과 보고는 전체 Head OK 검사보다 먼저 실행될 수 있으므로 보고 파일 존재를 보정 성공이나 Recipe 저장 완료로 해석하지 않는다.</li><li><strong>정리:</strong> Head 출력 OFF, 측정 관련 신호, 남은 이동 정리를 확인한 뒤 Stage 세션을 해제한다. 정리 실패가 나면 오류를 보존하며 단순 창 닫기를 정상 종료로 표시하지 않는다.</li></ol>
<p>실제 운전에서는 설비의 승인된 광학·인터락 절차를 따른다. 이 설명은 코드를 읽기 위한 순서이며, 현장 조건이 준비되지 않은 상태에서 레이저·축 명령을 직접 실행하라는 지시가 아니다.</p>
<h2>5. AUTO TPM과 보호윈도우의 연결</h2>
<p>CStationProcess의 Stage TPM 경로는 Stage ABLE 수신 뒤 Prepare, Measure, Save를 호출하고 Stage COMPLETE와 정리 신호를 확인한다. 따라서 파워 결과 저장, Stage COMPLETE, 신호 OFF가 각각 어디까지 확인됐는지 추적한다. TPM 완료와 보호윈도우 교체 완료를 하나의 상태로 합치지 않는다.</p>
<p>보호윈도우 교체의 기존 기준은 허용 가공매수 또는 다음 기판 ATT 예상의 2OR다. Job Change만 발생한 경우에는 파워보정 사유로 처리하는 기존 결정을 유지한다. 실제 Count 인계와 구간 이력은 제품 목표값과 별개이며, 교체 재시도 회수 소진을 품질 합격으로 표현하지 않는다. 상위 PPID/Job Change와의 완료 시점은 <ac:link><ri:page ri:content-title="05. A3 LD PPID·Recipe·OSS·Job Change"/><ac:plain-text-link-body><![CDATA[Recipe·OSS 계약]]></ac:plain-text-link-body></ac:link>에서 함께 관리한다.</p>
<h2>6. 운영자가 Power NG를 받으면</h2>
<ol><li>Recipe·Head·PowerMeter·ATT·Automation 대상, REAL/Simulation, 목표와 실제 W, 현재/목표 각도, 시각·시도 회수를 확보한다.</li><li>Stage의 위치·Busy·fresh·알람과 센서/ATT/Laser 연결 상태를 확인한다. 과거 정상 Snapshot을 현재 정상으로 쓰지 않는다.</li><li>측정 전 준비 실패, 통신 Timeout, 파싱 실패, 포화/측정조건 문제, 유효 측정 뒤 허용오차 초과를 구분한다.</li><li>목표 도달 실패라면 ATT 변화에 대한 실제 출력 기울기·범위·도착을 확인한다. 각도를 무작정 늘리거나 장비 한계를 넓히지 않는다.</li><li>중지·실패 뒤에는 출력 OFF와 측정 신호·이동 정리가 확인됐는지 검토한다. OFF가 불명확하면 파일 상태만 되돌려 복구 완료라고 하지 않는다.</li><li>승인된 조치 후 같은 조건으로 재현·회귀 검증하고 원인·조치·결과를 남긴다. 장비 교정과 코드 결함을 증거 없이 서로 대신 원인으로 지목하지 않는다.</li></ol>
<h2>7. 개발·변경 영향 검토</h2>
<p>명령 단위는 CTalonLaser, CConex_AGP, CBeamExpander, CPowerMeter와 CPicoMotor를 찾고 연결·상태는 CInterfaceManager에서 확인한다. ATT 이동은 CAttenuatorPositioningService와 Snapshot 서비스의 fresh·도착·한계 계약을 함께 읽는다. 보정 반복은 CPowerMeasureService, 실제 실행 경계는 CPowerMeasureRun, AUTO 연계는 CStationProcess, 저장은 CRecipeManager와 PowerTable/보고 파일 어댑터로 추적한다.</p>
<p>센서·ATT 공유 가능 여부를 바꾸면 Head 병렬 실행과 직렬화, 센서 대응, 보고 Simulation 판정까지 영향이 생긴다. Task/축 매핑을 바꾸면 CENTER와 출사 제어, 준비된 Script, Stage 세션의 소유권까지 검토한다. 응답을 빈 문자열이나 이전값으로 대체하는 편의 수정은 성공 판정과 오류 경계를 바꿀 수 있다.</p>
<h2>8. 인수 검증에 필요한 증거</h2>
<p>단위·프로토콜은 정상/빈/오류/늦은 응답으로, 준비는 센서 중복·Head 비활성·Task/축 중복·Stage Busy·stale 입력으로, 보정은 증가/감소 기울기·한계·목표 미달·시도 소진으로 검증한다. 중단 시점은 ATT 이동 전후·출사 전후·측정 중·결과 저장 전후로 나누어 출력과 파일 상태를 대조한다.</p>
<p>실장비 단계에는 측정 센서 교정·파장·장착·출력 안정성·반복성, Head별 결과와 실제 광학 구성, OFF/정리·신호 인계의 증거가 필요하다. 10월의 구현 공백이나 예제 테스트를 11월 완료 상태로 재사용하지 않고 현재 소스와 실행 로그로 항목별 판단한다. 시험 조건과 실제 결과가 없는 경우 완료 상태는 미확인으로 남긴다.</p><h2>실제 코드로 읽는 처리 흐름</h2><p>측정 결과를 보고하는 시점과 Recipe ATT 각도 저장을 허용하는 시점은 다르다. 아래는 실제 측정 종료부와 Save 메서드의 연속 발췌다. 보고 파일이 만들어졌다는 사실만으로 전체 Head 보정 성공 또는 Recipe 저장 완료를 판단하지 않는다.</p><h3>CPowerMeasureRun.Measure 종료부와 Save · 보고·정상판정·저장 Gate</h3><p><strong>코드 위치명:</strong> <code>CPowerMeasureRun.cs</code> · 본문에서 읽는 실제 구현 발췌</p><ac:structured-macro ac:macro-id="4260d0c9-a353-5edd-8b5a-d0b68e10428b" ac:name="code" ac:schema-version="1"><ac:parameter ac:name="language">csharp</ac:parameter><ac:parameter ac:name="title">CPowerMeasureRun.Measure 종료부와 Save · 보고·정상판정·저장 Gate</ac:parameter><ac:parameter ac:name="linenumbers">false</ac:parameter><ac:plain-text-body><![CDATA[            var started = false;

Save는 _measured와 결과 존재를 검사한 뒤 Recipe 각도를 저장한다. 따라서 NG·실패 과정의 보고나 측정 Table 실적도 남을 수 있지만 Recipe 각도 저장 성공과는 구분된다. 이 발췌는 Measure 내부 종료부부터 Save 전체까지이며 별도 실행 예제가 아니다.</p>
