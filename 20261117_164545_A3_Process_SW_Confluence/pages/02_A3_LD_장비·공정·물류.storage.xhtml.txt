<h2>전체 흐름 그림</h2><ac:image ac:width="1100" ac:alt="02. A3 LD 장비·공정·물류 설명 그림"><ri:attachment ri:filename="02_장비물류개념.png"/></ac:image><p>개념과 데이터 경계를 설명한 그림이다. 상세 조건·단위·미검증 범위는 아래 본문을 따른다.</p>
<p>기준: A3Drilling Ver11.17.0 · 9a43c709 · 2026-11-17. 기존 Ver11.13.0 분석에 인용된 관련 소스는 새 기준과 바이트가 같음을 확인했다. 이 페이지는 소스와 문서의 설명이며 장비 운전·정밀도·성능 합격 기록은 별도다.</p>
<h2>A3 LD가 하는 일</h2>
<p>A3 LD는 큰 기판 위에 반복 배치된 가공점을 여러 레이저 Head가 나누어 가공하는 시스템이다. Recipe는 어디에 어떤 조건으로 가공할지를 정하고, Stage는 기판을 이송하며, Scanner는 레이저 조사 위치를 빠르게 바꾼다. Vision은 기준 마크와 가공 결과를 측정한다. Process SW는 이들을 같은 기판과 같은 실행 회차로 묶는다.</p>
<p>가공점을 계산했다는 사실, Controller에 파일을 올렸다는 사실, 기판 가공이 끝났다는 사실은 각각 다른 단계다. 개발과 장애 분석에서는 이 세 가지를 먼저 나누고 마지막으로 품질 판정을 연결한다. 그래야 화면의 정상 표시를 실제 가공 결과로 오해하지 않는다.</p>
<h2>처음 읽을 때 알아둘 대상</h2>

<p>Shot 한 개와 광학 Beam 한 개는 같은 수량 단위가 아니다. DOE를 사용하는 Head에서는 한 Shot에 여러 Beam 자국이 대응할 수 있다. 설계 Shot 수, 실행 Shot 수, 검사 Beam 수를 한 숫자로 합산하지 않는다. Head 수와 활성 Head 수도 구분한다.</p>
<h2>장비 역할과 Process SW의 경계</h2>

<p>이 표는 기능 책임을 이해하기 위한 구성도다. 실제 PC 개수, 네트워크 주소, 배선과 장치 허용속도는 승인된 현장 자료가 필요하다. 같은 기판을 다루어도 Stage 상태, Scanner Task 상태, Vision 검사 상태는 각각 독립적으로 진행될 수 있다.</p>
<h2>기판이 이동하는 방향과 기준점</h2>
<p>2026-08-07 좌표 검증 프로젝트는 Review Camera가 선행하고 Scanner가 그 뒤에 있는 배치를 설명한다. 아래 순서는 그 문서의 물류 개념을 학습용으로 풀어 쓴 것이다. 최신 Main의 상세 handshake나 고객 승인 물류 시퀀스를 이 순서만으로 확정하지 않는다.</p>
<ol><li>Home에서 기판과 운전 조건을 준비한다.</li><li>정물류 방향으로 이동하며 Review 위치에서 AK 기준을 확인한다.</li><li>Scanner 뒤쪽의 반전 위치까지 이동한 뒤 진행 방향을 바꾼다.</li><li>역물류로 Scanner 아래를 통과하는 동안 Stage Encoder를 기준으로 MOF 가공한다.</li><li>가공점이 Review 위치에 도달하면 필요한 검사와 결과 수집을 수행한다.</li><li>결과·공정 완료를 정리하고 Home 복귀 또는 다음 물류 단계로 넘어간다.</li></ol>
<p>여기서 정물류·역물류는 경로 방향의 이름이다. 화면의 +Y·−Y, Scanner GY 부호와 자동으로 같아지지 않는다. 현재 코드는 STAGE_SCAN_DIRECTION_Y와 Head별 축 변환으로 방향을 계산하므로 좌표 설명에는 물류 화살표와 수치축 화살표를 함께 표시해야 한다.</p>
<p>Camera와 Head 사이의 기구 거리는 설치·Teaching의 기준값이다. 가공 후 측정한 Review Offset은 공정 오차를 보정하는 값이다. 두 값을 같은 종류로 저장하면 설치 오차와 가공 변화의 원인을 구분하기 어렵다. 기준값 변경과 보정값 변경은 기록에서도 나눈다.</p>
<h2>현재 Main의 두 운전 시작 경로</h2>
<table><tbody><tr><th>진입점</th><th>어떻게 시작하는가</th><th>설명에 포함할 경계</th></tr><tr><td>MAIN START / Semi Auto</td><td>MANUAL에서 초기 ProcessModel 준비 후 Station.Start</td><td>사용자 버튼을 누른 실행. <p>현재 AUTO prepare callback은 입력 사본의 SHIFT_OFFSET_X와 SHIFT_OFFSET_Y를 0으로 정규화한다. 수동 MOF에서 Shift가 반영된 결과를 봤더라도 같은 Shift가 AUTO에 유지된다고 설명할 수 없다. Shift 유지·확인창·초기화 옵션이 필요한지는 요구와 현 구현을 대조하는 별도 항목이다.</p>
<h2>한 장의 기판을 추적하는 진행 순서</h2>
<ol><li>어느 Recipe가 선택되었는지와 값 파일·공통 Setting·최신 Review Offset을 확인한다.</li><li>해당 회차 ProcessModel에 ProcessId, RecipeId, GlassId, LotId와 조건 사본을 묶는다.</li><li>Head별 점 목록을 만들고 실행 회차의 Script·좌표 CSV·Manifest를 생성한다.</li><li>Manifest에 적힌 실제 파일을 해당 Automation 대상으로 업로드한다.</li><li>요청 경로별 준비 gate와 MOF Ready RunId를 확인하고 Task 실행을 시작한다.</li><li>모든 대상 Head의 완료·정지·오류를 수집하고 필요한 Review·후속 검사의 합류를 확인한다.</li><li>Product 상태·판정·이력을 저장하고 상대측 완료응답과 신호 OFF까지 확인한다.</li></ol>
<p>이 목록은 개발자가 확인할 책임 순서다. Review와 0선 검사 등이 어느 이동 구간에서 병행되고 어디서 합류하는지는 각 시퀀스의 근거를 추가해야 한다. 전 공정을 무조건 한 줄 직렬 흐름으로 표현하면 병행 작업과 완료 조건이 가려질 수 있다.</p>
<h2>현상별로 먼저 확인할 것</h2>
<table><tbody><tr><th>현상</th><th>첫 확인</th><th>이어 확인할 증거</th></tr><tr><td>AUTO인데 시작하지 않음</td><td>Stage 요청 감시가 시작되었는지</td><td>요청 비트·ABLE·START·Busy·이전 cleanup 소유권</td></tr><tr><td>파일 생성 뒤 멈춤</td><td>업로드 성공과 준비 RunId</td><td>Head별 Manifest 파일·Controller·Task 상태</td></tr><tr><td>Head 일부만 움직임</td><td>활성 Head·배정 점 수</td><td>HeadNo/AutomationNo/TaskNo 매핑과 해당 Head 오류</td></tr><tr><td>화면 좌표와 가공이 다름</td><td>화면 입력과 준비 스냅샷 시점</td><td>Recipe·Offset 경로/시각·실제 Script 좌표</td></tr><tr><td>Completed인데 품질이 의심됨</td><td>수행 상태와 OK/NG 판정</td><td>공정 Skip 여부·Vision 실패·실측 출처</td></tr></tbody></table>
<p>원인 분석에서는 같은 시각이라는 이유만으로 다른 기판의 최신 로그를 붙이지 않는다. ProcessId·GlassId·RecipeId·Head·Task와 시간창을 먼저 맞춘다. 통신 정상·Task 실행·광학 가공·품질 판정은 각기 다른 증거가 필요하다.</p>
<h2>현재 설명의 적용 범위와 남은 확인</h2>
<p>Stage 요청의 Glass/Lot 정보는 현재 Product를 사용하거나 SIM/DUMMY 식별자를 생성하는 fallback이 있고, Stage 매핑 합의 후 바꾸라는 TODO가 남아 있다. 따라서 상위 PPID/SubPPID 자동 Job Change가 끝까지 완성되었다고 표현하지 않는다. 선택 레시피와 상위 요청 식별자가 정확히 연결되는 조건은 고객 계약 확인 대상이다.</p>
<p>기구 배치·실물 방향·Encoder 극성·속도·레이저 조건·광학 품질은 현장 평가 항목이다. 이 페이지 작성 과정에서는 레이저 조사, Stage 이동, 벤더 DLL 로드, Controller Script 실행과 실측 정밀도 시험을 수행하지 않았다.</p>
