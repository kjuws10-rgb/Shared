<h2>1. 처음 대응하는 사람의 확인 순서</h2>
<p>장애 대응의 시작점은 “어느 기판의 어느 단계에서 무엇이 기대와 달랐는가”다. 버튼을 여러 번 누르기 전에 현재 동작과 안전 상태를 확인하고, 최초 실패를 재구성할 자료를 남긴다. 이 페이지는 9a43c709의 정적 코드와 기존 분석을 바탕으로 작성한 초동 대응 안내이며, 아래 재현·검증표가 실장비에서 새로 통과했다는 의미는 아니다.</p>
<ol><li><strong>증상을 분류한다.</strong> 연결/응답 실패, 이동·Task 실패, 검사 NG, 보정 적용 차이, 저장·복구 문제 중 어디인지 나눈다.</li><li><strong>작업 식별자를 고정한다.</strong> 발생 시각, Glass/Recipe/Run, Head·Task·Cell·Shot·Beam과 현재 Step을 기록한다.</li><li><strong>기대한 값과 실제값을 나란히 놓는다.</strong> 명령/Actual, 요청/응답, raw/변환 오차, Current/Delta/Final처럼 같은 의미끼리 비교한다.</li><li><strong>원문과 버전을 보존한다.</strong> 원 결과·Offset·Recipe·I/F map과 관련 로그를 복사본으로 분석한다. 원측정을 EDIT해 현상을 숨기지 않는다.</li><li><strong>수정 전 재개 조건을 정한다.</strong> 어느 장치·신호·자료가 정상이어야 하며 어떤 증거를 남길지 담당자와 합의한다.</li></ol>

<h2>3. 증상별 초동 대응</h2>
<h3>3.1 Review는 끝났는데 보정이 바뀌지 않는다</h3>
<p><strong>읽기 확인:</strong> 결과 State=Completed, ResultSaveError 없음, 저장 파일 경로와 계획/결과 식별자·개수, NG 수를 확인한다. 일반 AUTO인지 0선 Follow-up인지 본다. <strong>판단:</strong> 일반 AUTO는 하나라도 NG면 전체 보정을 적용하지 않고 기존값을 유지한다. 0선 Follow-up은 전체 OK여도 검사만 한다. <strong>복구·재개:</strong> 원인/재검사 결과를 남기고 정상 저장된 새 Offset이 다음 DoReady에서 읽혔는지 확인한다. 표시만 보고 수동으로 같은 결과를 반복 Apply하지 않는다.</p>
<h3>3.2 보정값이 예상보다 크게 누적된다</h3>
<p><strong>읽기 확인:</strong> BASE→EDIT/REINSP 계보, 적용 날짜·경로, RESULT_SOURCE, DESIGN/SCANNER와 Current/Delta/Final을 비교한다. <strong>판단:</strong> 현재 중복 방지는 날짜·정규화 경로 기준이다. 새 Revision에 남은 과거 MEASURED delta가 다시 들어가는지는 별도 확인해야 한다. <strong>복구·재개:</strong> 추가 적용을 멈추고 가상 복사본으로 재현한다. 직전 활성 snapshot Rollback 범위와 준비 Script를 확인한 뒤 재개한다. 결과 Revision까지 원복됐다고 생각하지 않는다.</p>
<h3>3.3 1002 대기, CountMismatch 또는 촬영 결과 누락</h3>
<p><strong>읽기 확인:</strong> 해당 시도 1001의 UniqueId·길이·검색 식별자, frozen Trigger buffer, Stage IOF 개수·readback·이동 완료, 1002 응답과 1003 요청을 시간순으로 본다. <strong>판단:</strong> 통신 Timeout과 유효 응답의 표적 NG, Trigger 개수 불일치는 다르다. 실패 시도의 1003을 요청하지 않고 역순 버퍼로 새 시도하는 분기를 확인한다. <strong>복구·재개:</strong> 늦은 응답·이전 시도 결과를 현재 시도에 붙이지 말고 세션/신호 정리 후 승인된 재시도 조건을 확인한다.</p>
<h3>3.4 마스크가 있는데 검사점 또는 이동 경로가 이상하다</h3>
<p><strong>읽기 확인:</strong> 설계 Shot과 DOE footprint, Masking 제외 사유, Sampling 행, 최종 Use와 IOF buffer를 비교한다. <strong>판단:</strong> 점을 제외했다는 사실로 Stage 직선 경로 회피까지 입증할 수 없다. 첫/중앙/마지막 Sampling 줄이 막힌 경우 대체 줄 보장이 있는지도 구분한다. <strong>복구·재개:</strong> 최종 Trigger 위치와 실제 Encoder 경로를 함께 검증하고 물리 회피가 요구되면 별도 경로 사양으로 처리한다.</p>
<h3>3.5 Default 중앙·원빔·11번 대응 위치가 맞지 않는다</h3>
<p><strong>읽기 확인:</strong> 실제 Head별 DOE 유무·Zero Order 기준, 전역 격자값 1/4, AK1 Recipe 값과 AK3 설계 fallback/수동 입력의 출처를 본다. Default·First Offset·Review Offset을 단계별로 분리한다. <strong>판단:</strong> 원빔은 DOE 없는 실제 출사이며 16개 중 하나가 아니다. AK 두 X입력 평균은 새 실측·2D 회전 피팅이 아니다. <strong>복구·재개:</strong> 혼합 Head의 물리 구성과 좌표 대응 계약을 확인하고 승인된 Laser Off·저출력 절차로 따로 검증한다.</p>
<h3>3.6 Distortion을 수행했는데 다음 가공이 바뀌지 않는다</h3>
<p><strong>읽기 확인:</strong> 현재 Glass·Recipe·선택 DK 그룹, Base/LastLoad 단위·시각과 Load→Calculate→Save, Complete Handshake를 본다. <strong>판단:</strong> 수동 현재 map Load는 새 측정 요청이 아니다. Distortion 후에는 새 Align Offset으로 DoReady Script 재생성이 필요하다. <strong>복구·재개:</strong> 현재 준비 snapshot과 최종 Script의 같은 Shot을 비교한다. 별도 수명인 Review Offset 파일을 지워 해결하려 하지 않는다.</p>
<h3>3.7 보호윈도우 교체가 반복되거나 Retry가 소진된다</h3>
<p><strong>읽기 확인:</strong> Current/Max, 추가 Retry 0~3, Stage TrayCount 인계값, Request/Complete의 OFF 전환을 본다. <strong>판단:</strong> 교체 완료가 Count=0을 뜻하지 않는다. 현재 소진 경로는 LIGHT 알람 요청과 AUTO 계속이며 실제 배포 Alarm 정의를 확인해야 한다. <strong>복구·재개:</strong> 인계값 저장→보고→Request OFF 순서를 보존하고 임의로 Count를 초기화하지 않는다. 재시작 때 Retry 메모리 수명도 검토한다.</p>
<h3>3.8 재시작 뒤 NG 사유가 사라지거나 알람 원인이 맞지 않는다</h3>
<p><strong>읽기 확인:</strong> ReviewResult CSV의 VISION_RESULT_CODE/NG_REASON와 Active Product compact 저장을 분리 비교한다. 알람 후보와 실제 Glass/Run을 맞춘다. <strong>판단:</strong> 현재 Product 신규 NG 메타데이터의 writer/reader 공백, 최신 NG_SUMMARY의 Run/Glass 상관 공백이 정적 검토에서 확인됐다. <strong>복구·재개:</strong> 원 결과·원 로그를 유지하고 시간 근접 후보를 원인으로 확정하지 않는다. 저장·재로드와 두 작업 혼합 로그를 복사본으로 시험한다.</p>

<h2>6. 오래된 현황과 미확정 현장값을 관리한다</h2>
<p>공유된 2026-08-09의 고객 요구 51개, 공동 WBS 137개, 일정 36개는 당시 기준선이다. 이 표의 “구현완료”나 날짜 경과만으로 현재 현장 기능을 완료로 올리지 않는다. 현재 Commit의 정적 코드 확인, Simulation/UI 검증, 정식 Build, 실제 PLC·Stage·Laser·Vision 연동, 고객 Acceptance를 나누어 갱신한다.</p>
<p>현재 페이지들만으로 확정할 수 없는 항목은 실제 배포 I/F 주소·단위·극성·정상값, Head별 물리 광학 명단, 승인된 보정·정밀도·TACT 기준, Timeout/Retry 생산 정책, 재가공·배출 판단과 담당/승인 연락망이다. 각 항목에는 소유자, 결정일, 적용 버전, 시험 근거를 남겨 미결을 닫는다. 숫자나 담당자를 추정해 채우지 않는다.</p>

        }

ReadOptionalFiniteDouble은 유효값을 얻지 못하면 nullable 결과를 0으로 바꾸는 반면, ReadOptionalDouble은 공란만 0으로 처리하고 비정상 숫자는 예외를 낸다. 실제 결과 행의 ErrorX/Y를 읽는 경로는 앞의 optional finite 함수를 사용한다. 그러므로 0 표시만으로 실제 무오차 측정이라고 판단하지 말고 원문 열 존재·값·판정·측정 출처를 함께 확인한다. 원문이 잘못됐으면 단순 재적용 대신 올바른 결과 형식 또는 새 측정의 근거를 확보한다.</p>
