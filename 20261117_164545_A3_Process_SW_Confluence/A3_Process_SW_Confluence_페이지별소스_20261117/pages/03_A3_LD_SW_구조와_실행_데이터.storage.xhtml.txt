<h2>전체 흐름 그림</h2><ac:image ac:width="1100" ac:alt="03. A3 LD SW 구조와 실행 데이터 설명 그림"><ri:attachment ri:filename="03_실행데이터흐름.png"/></ac:image><p>개념과 데이터 경계를 설명한 그림이다. 상세 조건·단위·미검증 범위는 아래 본문을 따른다.</p>
<p>기준: A3Drilling Ver11.17.0 · 9a43c709 · 2026-11-17. 기존 Ver11.13.0 분석에 인용된 관련 소스는 새 기준과 바이트가 같음을 확인했다. 이 페이지는 소스와 문서의 설명이며 장비 운전·정밀도·성능 합격 기록은 별도다.</p>
<h2>구조를 읽는 기준</h2>
<p>프로그램을 처음 볼 때는 화면 이름보다 데이터의 소유자를 찾는 것이 빠르다. UI는 조작과 표시, Manager는 상태와 업무 규칙, File 계층은 저장 형식, Station은 동작 순서, Interface·Motion은 장치 호출을 맡는다. 한 숫자를 수정할 때도 누가 원본을 저장하고 누가 사본을 실행하는지를 구분해야 한다.</p>
<pre><code>CApp → CAppStartup → CManager → CRootView·메뉴
UI 요청 → Manager → Recipe/Setting/File 또는 Station
Station → 좌표·실행 모델 → Script 파일 → Automation/Interface → Controller
측정·실행 결과 → Review/Product → 파일·이력·화면</code></pre>
<p>이 화살표는 모든 클래스가 단방향으로만 참조한다는 뜻은 아니다. 개발자가 기능의 생산자와 소비자를 찾는 출발점이다. 실제 변경은 생성자 주입, 이벤트 구독, snapshot 공개와 파일 계약까지 따라가며 범위를 정한다.</p>
<h2>시작과 종료에서 생기는 시간 경계</h2>
<ol><li>CAppStartup이 Config 기준을 정하고 Recipe·Setting·Product·ReviewResult·ReviewOffset·Script 파일 어댑터를 만든다.</li><li>CManager가 정의와 캐시를 읽고 Interface, Automation, Motion, Product, Review, Recipe, Station을 구성한다.</li><li>manager.Initialize는 Task.Run으로 시작한다. RootView를 반환하고 창이 보이는 시점과 장비 초기화 완료 시점은 다를 수 있다.</li><li>RootView와 메뉴는 전달받은 Manager 객체를 공유하며 백그라운드 감시가 별도로 시작된다.</li><li>종료 시에는 호출된 Stop 경로와 별도의 Destroy 전체 정리 경로를 구분하여 연결 해제·이력 flush 범위를 확인한다.</li></ol>
<p>새 메뉴가 자체적으로 두 번째 Manager를 만들면 화면은 같은 장비처럼 보여도 캐시와 실행 소유권이 갈라질 수 있다. 기존 RootView가 전달하는 서비스와 데이터 객체를 재사용하는지 확인한다. 초기화 중인 상태를 단순한 IsConnected 하나로 표현할지도 실제 준비 조건과 함께 검토한다.</p>

<h2>같은 Parameter라도 네 가지 형태가 있다</h2>
<table><tbody><tr><th>층</th><th>담는 것</th><th>자주 생기는 혼동</th></tr><tr><td>항목 정의</td><td>Key·표시명·타입·단위·범위·Use·기본값</td><td>화면에 보이는 항목이면 이미 저장·실행된다고 생각함</td></tr><tr><td>Recipe/Setting 값</td><td>파일에 저장된 작업 조건 또는 설비 값</td><td>같은 이름의 Key와 Name을 무조건 동일시함</td></tr><tr><td>실행 Parameters·ProcessModel</td><td>이번 준비 시 합쳐진 조건 사본</td><td>파일을 바꾸면 이미 준비한 모델도 자동 변경된다고 생각함</td></tr><tr><td>Product·결과·이력</td><td>실행에 적용한 조건과 그 뒤의 상태·결과</td><td>다음 Recipe 편집값을 과거 기판의 조건으로 해석함</td></tr></tbody></table>
<p>현재 BuildRuntimeParameters는 입력 Dictionary를 복사하고 Option과 Motor Setting의 Key 값을 덮어쓴 뒤 최신 Review Offset을 넣는다. 같은 Key가 Recipe에도 있으면 실제 실행값은 설정 합성의 영향을 받을 수 있다. 따라서 Recipe 화면의 숫자만으로 실제 Script 입력을 확정하지 않는다.</p>
<p>Review Offset는 준비 당시 파일 경로와 저장시각이 함께 기억된다. 준비 뒤 다른 보정으로 바뀌면 최신성 확인이 다시 DoReady를 요구할 수 있다. Monitor 미리보기는 현재 선택 입력을 다시 계산하는 경로이므로, 이전 준비 모델과 시점이 맞는지도 따로 비교해야 한다.</p>

<table><tbody><tr><th>데이터</th><th>주요 식별·필드</th><th>목적</th></tr><tr><td>ST_RECIPE_DEFINITION</td><td>Id, Name, Parameters, History</td><td>편집·저장할 Recipe 한 개</td></tr><tr><td>ST_PROCESS_MODEL</td><td>ProcessId, RecipeId, GlassId, LotId, HeadPlans, Parameters, CreatedAt</td><td>해당 회차 실행의 묶음</td></tr><tr><td>ST_HEAD_PROCESS_PLAN</td><td>HeadNo, Laser/Speed/Ramp 조건, Shots, AutomationNo, TaskNo, ScriptFileName</td><td>Head별 실행 배정</td></tr><tr><td>ST_HEAD_SHOT_POINT</td><td>설계점·Scanner점·Offset 성분·Encoder 대기점</td><td>최종 좌표와 계산 중간값 추적</td></tr><tr><td>ST_SCRIPT_BUILD_RESULT</td><td>FilePath, HeadScripts, TotalShots, CreatedAt, MofReadyRunId</td><td>이번 회차 생성물과 준비 식별자</td></tr><tr><td>Product 데이터</td><td>기판 식별·Recipe 사본·Align/Distortion/Review·Runtime</td><td>기판 한 장의 상태와 결과 관리</td></tr></tbody></table>
<p>TaskNo의 기본값은 HeadNo지만 별도 property이며 AutomationNo도 따로 있다. 기본 설정이 같다는 이유로 세 식별자를 하나로 합치면 다중 Controller·Task 매핑에서 잘못된 대상으로 실행할 수 있다. 로그에도 필요한 세 번호를 각각 남겨야 한다.</p>
<h2>파일 형식과 영속화 경계</h2>
<p>현재 Main Recipe 값은 Tab,Name,Value의 첫 세 필드와 나머지 Extra를 읽는다. Setting 값은 헤더가 있는 TAB,NAME,VALUE 구조이고 Active Product는 TYPE,NAME,VALUE 구역형 기록이다. 항목 정의 CSV는 타입·단위·범위 등 더 많은 열을 갖는다. 이들을 하나의 Key,Value 형식으로 설명하면 로드·저장 문제가 생긴다.</p>
<p>8월 MOF WPF 샘플의 PPID 템플릿은 Key,Value였다. 그 샘플의 파일을 현재 Main의 Recipe 폴더에 넣으면 된다는 절차는 이 페이지의 지원 범위가 아니다. 변환이 필요하면 정의 Key, Tab, 값, Extra와 이력 계약을 검토하고 별도 사본으로 검증한다.</p>
<p>Product Active 파일은 메모리 객체 전체를 자동 직렬화하지 않는다. 명시된 구역·필드만 저장하고 Runtime은 로드 시 빈 초기 구조로 구성하는 부분이 있다. 기존 분석에서는 새 VisionResultCode·NgReason가 ReviewResult CSV와 달리 Product compact writer/reader에 남지 않는 공백을 확인했다. 결과 파일 저장과 앱 재시작 복구의 보존 범위는 각각 확인한다.</p>
<h2>상태를 한 개의 완료 표시로 합치지 않기</h2>
<p>기판의 Created/Running/Completed/Stopped/Error와 품질의 Pending/Skipped/OK/NG는 목적이 다르다. Completed이면서 Skipped인 경우도 있으므로 완료색만으로 실제 가공·검사 합격을 확정하지 않는다. Head별 상태와 Station 내부 단계, Controller Task 상태도 별도 계층이다.</p>
<p>Active 파일을 읽지 못한 상태에서 새 Product를 만들지 않도록 하는 경계와 실행 중단 복구가 있다. Running 흔적을 Stopped로 복구하는 것과 중간 Shot에서 자동 재가공을 시작하는 것은 다르다. 복구 화면에는 남아 있는 기판, 실행 조건, 완료한 작업과 재시작 허용 절차가 드러나야 한다.</p>
<h2>새 Parameter를 추가할 때의 진행 순서</h2>
<ol><li>이 값이 설비 공통인지 Recipe별인지 Cell/Shot/Head별인지, 단위와 좌표기준이 무엇인지 정한다.</li><li>정의 CSV의 Key·타입·범위·Use와 값 파일의 저장 규칙을 맞춘다.</li><li>Manager의 조회·검증·캐시 갱신·동시 수정 확인 경로를 연결한다.</li><li>BuildRuntimeParameters에서 덮어쓰기 또는 최신 Offset 합성과 충돌하는 Key인지 확인한다.</li><li>계산기·ProcessModel·Script·결과파일 중 실제 소비자와 추적 필드를 연결한다.</li><li>UI 표시·입력·적용완료와 저장실패 메시지가 commit 전후를 구분하는지 확인한다.</li><li>저장/재로드·준비/실행·앱 재시작을 분리하여 동일한 값과 출처가 유지되는지 검증한다.</li></ol>
<h2>장애를 좁히는 확인표</h2>
<table><tbody><tr><th>증상</th><th>확인 순서</th></tr><tr><td>저장했는데 화면이 옛값</td><td>저장 파일 → reload 결과 → Manager cache → UI 변경알림</td></tr><tr><td>화면값과 Script가 다름</td><td>선택 Recipe → Setting 동일 Key → 최신 Offset → 준비시각</td></tr><tr><td>재시작하면 결과 정보가 사라짐</td><td>메모리 필드 → writer 열 → reader 생성 → 복구 경로</td></tr><tr><td>장치가 두 번 시작되거나 정지가 늦음</td><td>실행 owner → worker/CTS → cleanup 완료 → 중복 클릭 gate</td></tr><tr><td>시작창은 떴는데 명령 불가</td><td>비동기 Initialize 결과 → 인터페이스/축 준비 → 인터락</td></tr></tbody></table>
<p>이 확인표는 소스에서 도출한 조사 순서다. 이번 문서 작성에서는 정상 설비 빌드·앱 시작·재시작 round-trip·벤더 장치 연결을 새로 실행하지 않았다. 소스 인용이 있다는 사실과 운전 시나리오를 통과했다는 사실을 분리하여 상태를 기록한다.</p>
