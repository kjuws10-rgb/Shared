키의 “설계 위치”와 “검출값”은 역할이 다릅니다.

Raw의 정확한 뜻: 이 화면에서는 스케일 변환 후, 화면 표시용 반올림을 하지 않은 mm 실수입니다. 현재 DOUBLE 맵은 이름과 달리 두 Word의 Int32 × READ_SCALE로 읽습니다. FLOAT 경로는 Float32입니다. 예를 들어 READ_SCALE=0.0001이면 정수 10000이 1.0000mm가 됩니다.

Base−Load의 부호가 현장 보정 방향과 맞는지는 Vision이 넘기는 값의 의미와 Head/Stage 방향 계약까지 확인해야 합니다. 과거 문서의 “현재−Benchmark 변위”와 부호가 반대라는 이유만으로 코드 오류라고 단정할 수 없습니다.

한 행의 좌/우 키Y (mm)좌/우 X (mm)

AK는 Glass 크기와 AK Margin으로 배치합니다. DK 설계좌표는 AK Margin + DISTORTION_KEYn_X/Y입니다. 현재 예제에서 오른쪽 DK는 X=908.5, 오른쪽 AK는 X=909.5로 서로 다릅니다.

04 · 라그랑주를 적용하는 정확한 위치

먼저 각 행을 X 직선으로 만들고, 그 행들을 Y 곡선으로 연결합니다.

① 행 안의 X 선형 보간

sⱼ = (x − xLⱼ) / (xRⱼ − xLⱼ)
rⱼ(x) = (1 − sⱼ)cLⱼ + sⱼcRⱼ

cL/cR은 그 행 좌·우 키의 (Base−Load X, Base−Load Y) 벡터입니다. 목표 X가 왼쪽에서 25% 지점이면 좌 75%와 우 25%를 섞습니다. 행마다 좌우 X가 달라도 각각의 폭으로 계산합니다.

② Y 전체를 라그랑주로 보간

t = (y − y₀) / (yₙ − y₀),　tⱼ = (yⱼ − y₀) / (yₙ − y₀)
Lⱼ(t) = Π(k≠j) (t − tₖ) / (tⱼ − tₖ)
C(x,y) = Σⱼ Lⱼ(t) rⱼ(x)

정규화는 Y좌표의 큰 수를 0~1 구간으로 바꾸는 계산상 처리입니다. 보정량 mm를 0~1로 줄이는 기능이 아닙니다. Lⱼ는 해당 행을 얼마나 반영할지 정하는 수학 계수이며 음수나 1보다 큰 값도 가능합니다.

③ 실제 코드는 같은 다항식을 barycentric 형태로 계산

wⱼ = 1 / Π(k≠j)(tⱼ − tₖ)
C = [Σⱼ {wⱼ/(t−tⱼ)} rⱼ(x)] / [Σⱼ {wⱼ/(t−tⱼ)}]

이 식은 위 라그랑주 다항식의 계산 형태입니다. 정확히 키 행의 Y에 도달하면 0으로 나누지 않고 그 행의 X 선형 값을 직접 반환합니다. 수학 형식의 참고자료는 NIST DLMF §3.3이며, A3 구현 여부의 근거는 아래 실제 소스입니다.

코드의 _weights ≠ 사용자 보정 가중치. 사용자 Start/End 배율 0.8을 곱하거나 상·하단에서 점진적으로 보정량을 줄이는 기능이 아닙니다. 현재 활성 보간 경로에서 그런 배율 적용은 확인되지 않습니다.

08 · Load Data의 실제 통신 흐름

주소 전체를 먼저 확인하고 순차 읽은 뒤, 성공한 묶음을 화면에 게시합니다.

온라인 Load는 연결, 주소 사용 여부, 읽기 권한, DOUBLE/FLOAT 형식, 읽은 값의 유한성을 검사합니다. UI는 확인 후 약 10초 취소 제한을 사용하고 선택·레시피·모드 변경을 점검합니다. 단, 진행 중인 native SDK 한 호출을 즉시 강제 중단하는 보장은 아닙니다.

Load 실패·Offline 경고 시 이전에 성공한 LastLoad가 남을 수 있습니다. 화면에 값이 보인다는 이유만으로 이번 기판의 새 측정이 성공했다고 판단하지 말고, Load 시각과 출처를 함께 확인해야 합니다.

현재 저장소 기본 맵 상태: ALIGN_LASTLOAD_AK1_X부터 DK6_Y까지 20항목은 모두 USE=0 / UNASSIGNED입니다. 읽는 기능과 사전 검사 코드는 있으나, 저장소만으로 실제 Vision 수신 주소 연결 완료를 판정할 수 없습니다.

Simulation 모드는 Base±1mm 난수를 만듭니다. 출처는 기록하지만 현재 Apply 경로가 Simulation 결과 저장 자체를 금지하지는 않습니다. 이를 실제 측정 데이터와 혼동하면 안 됩니다.

근거: S05, S08, S20. PR7의 수신 대기 개선은 이 데이터의 측정 의미·동일 Frame 계약을 새로 만들지는 않습니다.

09 · Apply 시 실제로 확인하는 항목

계산 전·계산 중·저장 직전에 각각 상태를 확인합니다.

순서확인 내용불만족 시
1. 선택·Load선택 레시피, Load 시각 존재, 선택 키 X/Y 값 존재, Load 당시와 키 위치 동일재선택·재Load 요청
2. 키 형상선택 키가 Glass 안에 있음, 좌우가 같은 Y, X폭>1e−9mm, DK행당 2개모델 생성 중단
3. 행 관계DK행이 상·하 AK 사이, Y행 간격>1e−9mm, 가중치 유한모델 생성 중단

5. 계산값유한값, 저장 범위 ±100000mm, 최종 0.001mm 반올림계산 중단
6. Tolerance반올림 후 |X| 또는 |Y|가 설정값보다 큰 Shot 찾기초과 목록 표시, 전체 취소 또는 나머지 적용 확인
7. 저장 직전레시피 ID/파라미터, 선택·Base/Load 입력, Tolerance가 계산 당시와 같은지 재검사다시 Apply 요청
8. 저장허용된 Shot의 두 축을 새 값으로 저장 → CSV 로그 저장로그 실패는 “레시피는 저장됨” 경고. 자동 Rollback 아님

여기서 ±100000mm는 데이터 저장 범위이지 공정 허용오차가 아닙니다. 또한 계산은 Head 사용 OFF나 Chess/Mask 출사 제외 여부로 미리 줄이지 않은 전체 설계 Shot을 대상으로 합니다. 따라서 실제 미출사 Shot 때문에 전체 범위 검사에 걸리는 경우도 확인해야 합니다.

10 · Tolerance 초과 시 기존 값은 어떻게 되나

초과 Shot은 두 축 모두 “기존 값 유지”입니다.

판정식

|계산 X| > T 또는 |계산 Y| > T

같은 값은 통과합니다. 벡터 길이 √(X²+Y²)를 검사하는 방식이 아닙니다. 최종 3자리 반올림 결과를 검사합니다.

한 축만 초과해도 그 Shot의 X/Y를 함께 제외합니다.

설정값의 세 가지 층

코드 기본값: 0.500mm
저장소 Setting.csv: 12mm
실장비 승인값: 미확인

12mm가 장비 정밀도 요구나 승인된 운전값이라는 뜻은 아닙니다.

최종 합산 관계

FinalScannerOffset = Recipe Offset + Head Default(변환)
　+ First Beam Offset(변환) + Review Offset(해당 형식 변환)
　+ Align Offset(설계→Scanner 변환)
Scanner 명령 = 이동 Stage 추종을 포함한 기본좌표 + FinalScannerOffset + X Shift 변환분

위 식은 Builder의 실제 합산을 요약한 것입니다. 모든 Offset이 같은 저장 좌표계라는 뜻은 아닙니다. Y Shift는 Stage 대기거리·기본 추종 좌표에도 반영되므로 마지막 항에 단순히 X/Y Shift를 통째로 다시 더하면 안 됩니다.

보정 단위는 DOE Shot 중심입니다. 한 Shot의 분기빔들은 중심 이동량을 공유하며, 16개 빔 각각을 개별적으로 구부리거나 각 빔의 내부 오차를 독립 보정하는 기능이 아닙니다.

13 · Auto / Manual 경계

저장된 보정을 사용하는 것과 매 기판 새 보정을 계산하는 것은 다릅니다.

현재 연결

Auto의 활성 Stage-master 경로

DoReady 시작 → 선택 Recipe snapshot → PrepareProcess → Runtime Parameter / 좌표 생성 → Head Script 생성·업로드.

이 과정에서 저장된 ALIGN_OFFSET을 사용합니다. LastLoad / CAlignInterpolation / Offset Apply를 자동으로 호출하는 연결은 확인되지 않습니다.

현재 연결

Manual MOF 경로

선택 Recipe / Head 조건 → RunManualMofAsync / ExecuteManualMof → PrepareProcessCore → 공통 좌표 Builder.

여기서도 저장된 Align Offset을 사용합니다. Manual Align 요청 버튼은 Stage 측 Align 요청·상태 표시이며, 이번 Lagrange Load·Apply까지 자동 완료하는 버튼이 아닙니다.

현행 Manual MOF Stage 이동 브리지는 Simulation 전용 허용 경계를 갖습니다. 공통 Builder 사용 확인을 실제 Manual MOF 실가공 검수 완료로 해석하지 않습니다.

따라서 현재 코드 기준으로 “레시피 선택 순간 매 기판 변형을 계산해 보관한다”, “Auto Align 완료라서 Lagrange 재계산도 끝났다”라고 설명하면 부정확합니다. 별도/기존 FSM의 Product Align·Distortion 완료 표시도 활성 Stage-master의 새 보간 완료 증거로 사용하면 안 됩니다.

Offset Apply 후 생성·업로드돼 있는 기존 Script를 그대로 쓰면 새 값이 반영됐다고 확정할 수 없습니다. 새 준비·재생성 경계에서 해당 Recipe snapshot을 사용했는지 확인해야 합니다.

14 · 보간 범위와 오버슈트

영역 밖은 막지만, 영역 안의 보정량이 측정 최대·최소를 넘을 수 있습니다.

범위 판정 Contains

Y는 최상·최하 AK행 사이여야 합니다. 해당 Y의 좌·우 경계는 이웃 행의 좌우 X를 선형 연결한 Polygon으로 정합니다. 그 밖의 Shot이 하나라도 있으면 전체 계산을 취소합니다.

Glass 사각형 안이라는 조건만으로 보간 가능하다고 볼 수 없습니다.

전역 다항식의 특성

행 값을 정확히 통과하되 내부를 측정 범위로 Clamp하지 않습니다. 이웃한 두 행만 쓰지 않으므로 먼 행의 이상값도 다른 위치에 영향을 줄 수 있습니다.

정확한 보간 ≠ 측정하지 않은 내부의 정확도 보장.

왼쪽 예제는 같은 간격의 세 Y행에서 키 보정이 모두 0~+0.010mm여도 내부에서 −0.00125mm가 나옵니다. 오른쪽 예제는 Y행=0/5/10, 위·아래 행 보정=0, 중간 행의 좌(X=2) 보정=0·우(X=8) 보정=+0.060mm입니다. 전체 Polygon 안의 (1,2.5)를 평가하면 중간 행은 X외삽으로 −0.010mm, 그 행의 Y계수는 0.750이 되어 최종 −0.0075mm가 됩니다. “외삽이 전혀 없다”는 설명은 부정확합니다.

확인 방향: 키만 검사하지 말고 전체 Shot의 보정량 분포, 극값, 인접 Shot 간 변화량을 함께 봐야 합니다. 이것은 보완 제안이며 현재 코드에 해당 추가 제한이 구현됐다는 뜻은 아닙니다.

근거: S01 및 독립 순수 계산 시험. Contains의 경계 선형 연결과 Evaluate의 전역 Y 계산은 용도가 다릅니다.

15 · Review 보정·Masking과의 관계

Align과 Review는 최종 좌표에서 함께 더해집니다.

보정현재 저장 동작Distortion과 구분할 점
Align / LagrangeShot별 ALIGN_OFFSET을 새 값으로 대체AK/DK Base−Load를 공간 보간
Simple선택 범위 Review Offset을 입력값으로 대체Align 필드를 대신하지 않음
Rough / Fine기존 Review Offset에 계산값 누적이미 적용한 Align 상태에서 측정한 잔차인지 확인 필요

Fine에는 같은 UI 결과의 재적용을 막는 상태가 있습니다. 그러나 측정 결과의 기준 Recipe를 비교할 때 이름에 OFFSET이 들어간 필드를 제외하므로, Align/Simple/Rough/Default 변경 이후에도 기존 Fine 결과가 같은 기준 세대로 간주될 수 있는 경계가 있습니다. 중복 보정이 언제나 방지된다고 설명할 수 없습니다.

Masking은 별도이며 최종 Offset의 영향도 받습니다.

현재 Masking은 Group 위치에 FinalScannerOffset X/Y를 포함해 Beam footprint를 평가하고, Script가 그 결과와 Chess 조건으로 출사 여부를 결정합니다. 과거 설명용 HTML의 “원 Gate 유지”를 현재 코드 설명으로 그대로 가져오면 안 됩니다.

Head XY Flip·Cell 회전·최종 Scanner Offset을 Masking의 Cell 좌표에 반영하는 계약은 별도 검증 대상입니다. 이번 작업은 소스 연결을 확인한 것이며, 실제 장비의 Masking 오류를 재현한 것은 아닙니다.

18 · 자주 혼동하는 질문

짧은 질문으로 다시 정리

DK를 모두 해제하면 Distortion 보정이 꺼지나?

아닙니다. AK4로 X/Y 선형 보간을 합니다. 저장된 Shot Offset을 지우려면 Offset Init이 필요합니다. DK 선택 변경만으로 이미 저장한 값이 자동 변경되지는 않습니다.

Base Init이나 Load to Base를 누르면 기존 보정도 0이 되나?

아닙니다. Base와 저장 Shot Align Offset은 별도입니다. 새 Base와 동일한 Load로 다시 Apply해야 계산값이 0이 되며, 별도 Offset Init으로 직접 지울 수 있습니다.

Load를 누르면 새 측정과 Align 동작도 시작하나?

아닙니다. 이미 MELSEC에 존재하는 값을 읽습니다. Vision 측정 완료·같은 Glass인지의 확인 절차가 별도 필요합니다.

키를 정확히 통과하면 기판 안쪽도 정확한가?

그렇지 않습니다. 내부는 선택한 모델의 추정입니다. 측정 오차·관측하지 못한 X방향 굴곡·오버슈트·촬영 좌표계 오차가 남을 수 있습니다.

Apply를 두 번 누르면 보정이 두 배가 되나?

Align은 같은 입력으로 계산한 새 값으로 대체하므로 정상 동일 조건에서는 누적되지 않습니다. 반면 Review Rough/Fine은 별도의 누적 방식이므로 구분해야 합니다.

현재 화면의 차이와 저장값이 약간 다를 수 있나?

예. 화면 Base−Load는 표시용 반올림 문자열끼리 빼지만, 보간은 반올림 전 Raw 값으로 계산합니다. 화면 차이와 입력 차이는 0.001mm 수준에서 다를 수 있고, 최종 저장도 1µm 단위입니다.

이번 MELSEC PR7 병합으로 Distortion 자동화까지 완료됐나?

아닙니다. PR7은 공통 수신·Monitor 표시 대기 개선입니다. Distortion 수학·Recipe·Review 적용 파일은 이전 main과 같으며, 같은 측정 세대 보장이나 Auto Lagrange 호출을 새로 추가하지 않았습니다.
