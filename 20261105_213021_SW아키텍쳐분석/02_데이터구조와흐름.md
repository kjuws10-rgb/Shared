## Vision wire 형식

capacity는 **예약한 전체 배열 칸 수**, Count는 **실제 유효한 점 수**입니다.

| 명령 | 현재 본문 | 기본 capacity300 예 |
| --- | --- | --- |
| 1001 Flying Ready 요청 | 8 + 24×capacity bytes. Count 뒤 미사용 칸은 모든 필드−1 | 7,208 bytes |
| 1002 Move Done 응답 | Int32 수량 판정: 0일치 / 1불일치 | 4 bytes |
| 1003 Flying Result 응답 | 8 + 36×capacity bytes. 유효 Count개만 결과로 사용 | 10,808 bytes |

1001의 capacity를 같은 라인의1003에도 유지하며, 헤더16bytes→선언된 body를 정확히 읽는 수신 구조와 UID/명령 대조를 사용합니다. [프레임 수신 329–340](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a966ebf527f9ff0f52b1d84a891fda6fc6fc3e6f/Drilling.Common/Interface/Vision/CVisionComm.cs#L329-L340) · [응답 UID·명령 대조 272–298](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a966ebf527f9ff0f52b1d84a891fda6fc6fc3e6f/Drilling.Common/Interface/Vision/CVisionComm.cs#L272-L298) · [1001 배열 576–594](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a966ebf527f9ff0f52b1d84a891fda6fc6fc3e6f/Drilling.Common/Interface/Vision/CVisionComm.cs#L576-L594) · [1002/1003 해석 734–802](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a966ebf527f9ff0f52b1d84a891fda6fc6fc3e6f/Drilling.Common/Interface/Vision/CVisionComm.cs#L734-L802).

이 소스의1002 수량 판정0/1은 mark.Result의 검색 성공 판정과 다른 필드입니다. mark.Result는 기존부터 `>0`을 성공 후보로 사용하며 상대 계약은 별도 확인해야 합니다.

## 측정값과 보정값의 단위

```text
오차(mm) = CameraResolution(mm/pixel) × nResolution × (Target − Hole)
          → Vision Flip → X/Y 허용오차 판정
```

기본 CameraResolution은0.0025mm/pixel입니다. 종전 일반 Review의 Hole−Target 또는 일부 경로의 원시 차이를 그대로 사용하던 방식과 의미가 달라졌습니다. 같은 CSV 열 이름이어도 과거 파일의 오차와 단순 합산하면 안 됩니다.

전체 AUTO FINE이 OK일 때만 Cell·Shot별 보정량을 구하고, 기존 보정을 DESIGN 좌표로 정규화한 뒤 누적 저장합니다. 새 파일 경로는 `Config/RECIPE/{Recipe}_reviewoffset/{시각}_reviewoffset.csv`이고 열은 CELLID/SHOTID/REVIEWOFFSETX/REVIEWOFFSETY/COORDINATE_SPACE입니다. 기존 SCANNER 파일 읽기 호환은 유지합니다. [보정 모델 10–25](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a966ebf527f9ff0f52b1d84a891fda6fc6fc3e6f/Drilling.File/ReviewOffset/CReviewOffsetFile.cs#L10-L25) · [보정 파일 저장 61–103](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a966ebf527f9ff0f52b1d84a891fda6fc6fc3e6f/Drilling.File/ReviewOffset/CReviewOffsetFile.cs#L61-L103) · [AUTO 누적 저장 78–119](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a966ebf527f9ff0f52b1d84a891fda6fc6fc3e6f/Drilling.Common/Review/CAutoFineReviewCoordinator.cs#L78-L119).

일반 Review의 Product 상세 결과 갱신과 AUTO FINE의 결과/Offset 저장은 경로가 다릅니다. AUTO FINE에 Product Review 상세 갱신까지 직접 연결됐다고 해석하지 않습니다.

## 데이터 삭제가 현재 동작에 미치는 영향

| 삭제 대상 | 새 checkout에서의 영향 | 구분 |
| --- | --- | --- |
| 최신 Nov2 Review Offset | 남아 있는 Oct26 파일을 최신으로 선택. 같은20,740 Shot 중2,380행 값 변경 | 실제 가공 입력 변경 가능 |
| Data/AlignOffset 4개 | 저장 로그 삭제. 가공은 Recipe의 저장 ALIGN_OFFSET을 사용 | 보정 초기화와 다름 |
| Data/Product/ActiveProduct | 파일 부재 시 current=null, 재시작 복구점 없음 | 로드 즉시 새ID 생성은 아님 |
| Review/Beam 결과 | 지정 파일 조회는 파일부재 오류, 최근 Beam 결과는 없으면null | 결과 열 형식 변경은 아님 |

Review Offset의 Cell1/A1 예는 `(0,0)`→`(0.230,1.016)mm`입니다. 삭제 전 파일 전체가0이었다는 뜻은 아닙니다. 두 파일의 Shot identity는 같고0이던2,380행이 이전 nonzero값으로 돌아옵니다. **현장에 기존 파일을 남긴 업데이트라면 Git checkout과 효과가 다릅니다.**
