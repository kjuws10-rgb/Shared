# 데이터 구조와 저장 형식

## 저장 데이터와 실행 데이터를 나누어 보기

레시피 CSV는 작업 조건의 원본입니다. 프로그램은 이를 읽어 Cell·Model·Shot·Beam·Head별 실행 좌표와 Review 대상 목록을 만듭니다. 그 실행 자료는 파일에 있는 값 그대로가 아니라 좌표 변환·마스킹·선택 규칙을 거친 메모리 자료입니다. 측정 결과와 다음 가공에 사용할 보정값은 다시 별도 파일로 저장됩니다.

~~~mermaid
flowchart TD
  A["JHMI 정의와 Recipe CSV"] --> B["RecipeManager의 현재 레시피"]
  B --> C["Cell Model Shot Beam과 Head 배정"]
  C --> D["마스킹과 Scanner 좌표 계획"]
  C --> E["Review 대상과 Sampling"]
  E --> F["Vision 측정 결과"]
  F --> G["ReviewResult 파일"]
  F --> H["Rough Fine 측정 보정"]
  U["사용자 Key in"] --> SI["Simple 입력 보정"]
  SI --> I
  H --> I["Shot별 ReviewOffset 파일"]
  I --> D
  J["정상 가공과 Stage 인계"] --> K["Recipe CSV의 현재 보호윈도우 매수"]
  K --> B
~~~

## 저장 계약의 변화

| 자료 | 저장 형식과 소유자 | 이번 변화 |
| --- | --- | --- |
| Recipe | Config/RECIPE의 TAB NAME VALUE CSV | CURRENT_PROCESS_COUNT 행 추가와 런타임 갱신 |
| JHMI 레시피 정의 | TAB GROUP NAME 자료형 단위 범위 표시 순서 | ProtectWindow 그룹과 숨김 현재 매수 정의 추가 |
| MELSEC Map | ID USE 주소 자료형 방향 접근 배율 길이 주기 설명 14열 | 102행에서164행, 활성42에서64행 |
| Review 설정 | 기존 Config/ReviewSetting의 NAME VALUE 기반 .review | 저장 서비스와 소비 경로 제거 |
| ReviewOffset | CELLID SHOTID REVIEWOFFSETX REVIEWOFFSETY COORDINATE_SPACE | 5열 저장 계약 유지, Shot별 적용·검증 변경 |
| ReviewResult | 업무별 CSV와 측정 상태·식별 정보 | 0선 별도 결과 및 시뮬레이션 출처 기록 확장 |
| Product | 현재 제품 TYPE NAME VALUE와 History CSV | 관리 클래스 변경이 있으나 RecipeID·Glass 등 연결의 역할 유지 |

[영역별 tree 비교](schema-diff.json)는 파일 변경 여부를 나타냅니다. 이번에는 Config·Recipe·Review·Correction·Vision·Station·Product·File의 비교 대상 tree가 모두 달라졌습니다. tree가 다르다는 이유만으로 모든 CSV 열이 바뀌었다고 판단하지 않았습니다.

## 보호윈도우 현재 매수

[CProtectWindowRecipeData](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Managers/CRecipeManager.cs#L371-L384)는 `MAX_PROCESS_COUNT`와 `CURRENT_PROCESS_COUNT`를 구분합니다. 현재 매수는 음수·소수·비유한수·int 범위 밖 입력을 거부합니다.

[저장 구현](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.File/JHMI/CJhmiRecipeFile.cs#L1395-L1452)은 현재 Recipe 파일을 읽어 해당 행만 교체하고, 임시 파일을 flush한 뒤 원본 Recipe 경로로 이동합니다. 매수 갱신마다 전체 레시피 편집 이력을 새로 만드는 경로가 아닙니다. [일반 저장](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.File/JHMI/CJhmiRecipeFile.cs#L184-L205)은 예전에 열린 편집본이 최신 런타임 매수를 덮어쓰지 않도록 기존 파일 값을 우선합니다.

예제 `test0929`는 MAX가0에서20으로 바뀌고 CURRENT=2가 추가됐습니다. 다른 예제 Recipe에도 현재 매수 행이 추가됐습니다. 이 숫자는 Git에 포함된 설정값이지 실제 보호윈도우의 잔여 수명 검증 결과가 아닙니다.

주의할 점은 **MAX=0이 사용 안 함이 아니라 즉시 교체 요청 조건**이라는 것입니다. [요청 판정](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Station/CStationProcess.cs#L4144-L4174)은 current가maximum 이상인지 검사하며 같은 Glass cycle의 중복 요청을 별도로 막습니다. 과거0을 비활성으로 사용했다면 배포 전에 의미를 재확인해야 합니다.

## 레시피 복사와 부가 폴더

[RecipeManager 작업 gate](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Managers/CRecipeManager.cs#L72-L105)와 [File의 선택 복사](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.File/JHMI/CJhmiRecipeFile.cs#L1284-L1353)가 추가됐습니다. 선택한 보정 등 부가 폴더를 staging에 준비하고 폴더가 준비된 뒤 새 Recipe CSV를 공개하며, 실패 시 이번에 만든 폴더를 정리합니다. 새 복사본의 런타임 현재 매수는0으로 시작합니다. rename/delete도 부가 폴더와 함께 처리하는 경로로 확장됐습니다.

부가 폴더 소유권은 `{RecipeId}_` 접두사로 찾습니다. 따라서 A와A_B처럼 이름이 겹치면 A_B의 폴더가 A의 후보에 포함될 수 있습니다. 운영 중 실제 사고를 재현한 것은 아니며, 이름 중첩·선택 취소·잠긴 파일·rollback을 별도 fixture로 확인할 조건부 위험입니다.

## MELSEC Map과 숫자의 의미

열 구조는 유지되지만 주소와 활성화 범위가 달라졌습니다. [현행 맵](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Config/JHMI_MELSEC_MAP.csv#L24-L75)에서 기존 ID2개의 주소가 바뀌고,62개 ID가 추가됐습니다. 기존40개 ID는 설명만 바뀌었습니다.

| 값 | 현행 주소 | 자료형과 의미 |
| --- | --- | --- |
| TPM ABLE | W804A | 기존 W8218에서 이동, logical1은raw10000 |
| TPM COMPLETE | W804C | 기존 W821C에서 이동 |
| 후속 Review 요청 | W8218 | TPM이 아닌 별도 후속 Review 요청 |
| Stage 속도 | W8032 | mm/sec, WRITE_SCALE10000 |
| 실제 가공 완료 | W8034 | 전체 Task 정상 완료값, Process COMPLETE와 분리 |
| 보호윈도우 교체 요청 | W804E | 가공SW가 게시 |
| 보호윈도우 현재 매수 보고 | W8052 | Recipe의 현재 매수를 배율 적용해 게시 |
| Stage 매수 인계 | WC2B0 | 1Word 원시 count, 배율1 |
| 교체 Section 완료 | WF150 | 정상 완료 수신 후 매수 저장·보고·요청OFF |

같은 숫자1이라도 `WC2B0`의 원시 매수와 상태 신호의logical1은 다른 단위입니다. 배율을 두 번 적용하거나 모든 Word를10000으로 나누면 안 됩니다. 맵 설명의 Spec0.08 표기는 저장소의 명세 주석이며, 실제 PLC 프로젝트와 교차 승인된 사실까지 검증한 것은 아닙니다.

62개 신규 ID 중22개만 활성입니다. Align Base 보고·Encoder·여러 PTW Busy/결과/평탄도·옵션 주소는 USE=0인 항목이 남습니다. 주소가 적혔다고 자동으로 보내거나 안전 인터락에 사용되는 것은 아닙니다.

## Review 설정 파일과 샘플링은 다른 기능

예전 `.review` 파일을 다루는 File/Base/시작 주입은 사라졌습니다. 따라서 기존 파일이 남아 있다는 사실만으로 현재 버전에서 불러오고 저장한다고 볼 수 없습니다. 이전에도 실제 메뉴의 저장 호출까지 연결된 근거는 확인되지 않아, 정상 운용하던 기능의 고장으로 단정하지 않습니다. 반면 [ReviewRulePlanBuilder의 Edge와 Center 선택](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Review/CReviewRulePlanBuilder.cs#L466-L499)은 남아 있습니다. 즉 **선택 알고리즘 일부는 유지됐지만 독립 설정 파일 서비스는 제거됐고 현재 운용 연결은 없습니다.**

제품별 Review 조건을 재시작 후 복원해야 한다면 Recipe·RunOption·별도Review파일 중 어느 자료가 원본인지 먼저 확정하고 UI부터 File까지 다시 연결해야 합니다. 기존 정책이 이미 새로운 저장 계약으로 완전히 대체됐다고 판단할 근거는 없습니다.

## 보정값의 좌표 공간과 출처

[Shot별 보정값 읽기](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Recipe/CShotCoordinatePlanBuilder.cs#L249-L265)는 해당 Shot의 축 값이 없으면0을 사용합니다. 과거 전체 `REVIEW_OFFSET_X/Y`를 fallback으로 사용하는 동작은 제거됐습니다. 전체 보정값만 있던 오래된 Recipe는 이전과 같은 가공 결과를 낼 것이라고 가정하면 안 됩니다.

[파일 병합](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Recipe/CShotCoordinatePlanBuilder.cs#L1096-L1160)은 유한수·Cell/Shot 식별·중복을 확인한 뒤 기존 키를 교체하는 방향입니다. `COORDINATE_SPACE=DESIGN`과 `SCANNER`는 같은 X/Y 숫자라도 적용 기준이 다릅니다. File 계약이5열로 같아도 병합·fallback 의미의 변화는 별도로 검수해야 합니다.

Git에 추가된 최신 test0929 보정 파일에는20,740개 Shot 행이 있고 DESIGN 보정 X는약−1.103~3.020mm, Y는약−1.197~1.203mm입니다. 같은 시각대 ROUGH 결과에는 Stage/Vision SIMULATION=ON이 기록돼 있습니다. 보정 CSV 자체에는 시뮬레이션 출처를 식별하는 열이 없으므로 이를 생산 보정값으로 승인해서는 안 됩니다. 자세한 로딩·제한 문제는 영향 분석과 위험 목록에 정리했습니다.

## 결과 파일과 Product 연결

기존 일반·Beam·Rough·Fine 결과의 열 형식과 Product Active/History의 계약은 유지됩니다. Fine는 [실제 StageSimulation 상태](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.File/ReviewResult/CReviewResultFile.cs#L446-L577)를 저장하도록 바뀌어, 예전처럼 무조건ON을 쓰는 것과 구분합니다.

신규 [0선 결과 저장](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.File/ReviewResult/CReviewResultFile.cs#L701-L733)은 `Data/ZeroDefence/yyyyMMdd` 아래 RunId가 들어간 CSV를 임시 파일에서 원자적으로 공개합니다.30열에 Recipe·Glass·Group·Head/Cell/Shot/Beam·ReviewX/StageY·Resolution·원시Target/Hole·변환 편차·Judge·Stage/Vision Simulation·Tolerance·Flip을 담습니다. 결과가 저장됐다는 사실과 보정 적용 승인은 같지 않습니다. 0선 결과는 이 경로에서 ReviewOffset 파일로 적용하지 않습니다.

ProductManager/File의 메서드와 저장 헤더는 실질 변화가 없지만, 새 AUTO Fine 실행 경로의 Product.Review 상태·결과 이력 갱신까지 연결됐다고 볼 호출은 없습니다. 일반 Review의 Product 갱신과 AUTO Fine의 FineMonitor/CSV/Offset 저장을 구분해야 합니다.
