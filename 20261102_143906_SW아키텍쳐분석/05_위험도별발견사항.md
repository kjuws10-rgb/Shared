# 위험도별 발견사항과 우선순위

P0는 이번 소스의 빌드 차단, P1은 배포 전 반드시 해결하거나 운전 범위를 제한해야 할 항목, P2는 호환성·복구·운영 계약 확인 항목입니다. 코드 결함으로 확인한 것과 정적 검토에서 남은 위험을 구분했습니다. 이 보고서를 작성하면서 생산 소스를 수정하지 않았습니다.

## P0 로그 구현 누락으로 최신 소스 빌드 실패

**확인된 결함입니다.** 최신 Release 빌드는 오류19·경고0으로 실패했고, 같은 환경의 기준 버전은 오류0·경고0으로 성공했습니다. Common의 로그 파일6개 삭제 후 `CLogManager` 참조가 남습니다. [CManager](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Managers/CManager.cs#L1-L30)와 [시작부](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.UI/CAppStartup.cs#L20-L36)가 이를 요구합니다.

새 [gitignore](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/.gitignore#L1-L6)의 `Log/`는 실제 로그 데이터뿐 아니라 소스 폴더 `Drilling.Common/Log`에도 적용됩니다. **로그 소스와 로그 데이터의 제외 범위를 구분하고 필요한 tracked 소스를 복구한 뒤 전체 빌드해야 합니다.** 누락 원인을 Gitignore 하나로 단정하지 않았으며, 19개 오류가 이 버전의 모든 오류라는 뜻도 아닙니다. Common 이후 File/UI 컴파일과 런타임은 확인되지 않았습니다. 남아 있는 `.buildcheck` DLL을 복사해 빌드를 우회하지 않았습니다.

## P1 지난 MELSEC 지연 개선과 시험이 제거됨

**소스 제거는 확인됐고, 실제 지연 악화 수치는 미측정입니다.** [현재 Run](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Interface/Melsec/CMelsec.cs#L191-L215)은 active Write가 있으면 그것을 처리하고 Poll1개를 수행한 뒤 돌아갑니다. 지난 최대4블록 수집과 Readback 대기 중 큐선두 일반 Read 처리가 없습니다. [현재 Readback 대기](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Interface/Melsec/CMelsec.cs#L1211-L1224)는 다음 시각 전이면 바로 반환합니다.

활성MELSEC100ms 전용 UI 타이머와 수신·적용·블록진단이 사라졌고 [2초 화면 gate](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.UI/CRootView.cs#L1878-L1931)로 돌아갔습니다. Write draft를 보존하는 행 갱신은 남아 있으므로 화면 기능 전체 삭제와 구분합니다. 기존 회귀 프로젝트2개도 없어 이전19/30 통과를 최신 버전에 인용할 수 없습니다. 의도한 성능 정책을 확인하고 복구·재시험해야 합니다.

## P1 시뮬레이션 보정값의 생산 유입 방어 부족

**출처 구분과 범위 승인 공백이 남습니다.** 최신 test0929 보정 CSV는20,740행의 DESIGN 자료이고 최대 절대X가3.020mm입니다. 같은 날 ROUGH 결과는 Stage/Vision 시뮬레이션으로 기록돼 있습니다. 파일의 발생 원인·실제 승인 여부는 저장자료만으로 단정하지 않았습니다.

[입력 검증](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Recipe/CShotCoordinatePlanBuilder.cs#L1096-L1160)은 숫자·식별·중복을 확인하지만, 보정 파일의 생산 승인 출처·교정 세대·시뮬레이션 여부를 별도 열로 강제하지 않습니다. 단순히 가장 최근 파일이라는 이유로 승인하면 안 됩니다. 승인된 파일 선택, 모드/Recipe/설비/측정 세대, 최대 보정량과 좌표 공간을 연결한 배포·로딩 gate가 필요합니다.

## P1 0선 선대기는 실기 가능하지만 본 검사는 차단

**확인된 연결 비대칭입니다.** [선대기 모니터](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Station/CStationProcess.cs#L5472-L5560)는 실제 X 이동을 사용할 수 있지만 [본 Prepare](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Station/CStationProcess.cs#L5620-L5647)는 실제 MELSEC에서 예외를 냅니다. 실기에서0선ON을 허용할지, 먼저 어떤 계약·모션을 검증할지 명확히 해야 합니다. “시뮬레이션 전용이라 아무 축도 안 움직인다”는 안내는 부정확합니다.

## P1 0선 실기 계약과 자료 버전의 기준 확정 필요

현재 [포인트 루프](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Station/CStationProcess.cs#L5660-L5704)와 [Vision session](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Review/CReviewManager.cs#L3065-L3118)은 포인트별1001·1002·ACK일 때1003을 반복합니다. 새로 첨부된 시나리오 평가표의 Process 도형은 이 주기와 일치합니다. 기존 [Y Flying 단일 세션 기준](https://github.com/kjuws10-rgb/Shared/tree/main/20261025_161154_A3_Zero_YFlying_Patch)은1900·1001·N개Grab·1002·필요1003을 전체1회로 정의하므로, 자료 버전 간 충돌입니다. 새 첨부 대비 구현 불일치로 단정하지 않았습니다. 최종 승인 계약을 정한 뒤 Count·ACK/NCK·결과 식별·타임아웃과 StageBuffer 촬영 구간을 함께 검수해야 합니다.

Resolution을 기록하면서 Target−Hole을mm로 취급하는 임시 계약도 실기 Vision의 단위와 대조해야 합니다. 정책을 소스에 맞춰 조용히 바꾸지 않고 차이로 남겼습니다.

## P2 보호윈도우의 복구와 남은 조건

현재는 매수 기반 요청·인계 저장입니다. 고객사 기준의 매수 OR 예상ATT 중 ATT 분기와 교체 후 TPM·재측정·평탄도 결과는 별도 작업입니다. MAX=0은 즉시 요청이므로 비활성 의미로 사용하지 않아야 합니다.

[재시작 복구](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.Common/Station/CStationProcess.cs#L4350-L4424)는 첫 관측ON/ON을 받아들일 수 있고 pending Recipe가 없으면 현재 선택 Recipe를 사용합니다. 이전 요청의 Recipe·Tray·완료 세대가 다를 때 잘못된 매수가 인계되지 않도록 시나리오 검증이 필요합니다. 코드만으로 실제 오동작을 재현한 것으로 표현하지 않았습니다.

`CURRENT_PROCESS_COUNT`는int 범위를 허용하지만 W8052는scaled32-bit 값입니다. 오래 유지되는 큰 count의 전송 범위와 상한도 명세에 맞춰야 합니다. 실제 현장 최대매수가 훨씬 작다면 그 제한을 UI·파일·PLC에 일치시키는 방식으로 검수할 수 있습니다.

## P2 Review 설정 저장소의 부재

기존 `.review` File/Base와 시작 주입을 제거했습니다. 다만 이전 버전에서도 주입된 객체가 실제 메뉴의 저장·불러오기 동작으로 이어지는 호출은 확인되지 않았으므로, **정상 운용하던 기능이 갑자기 고장 났다고 단정하지 않습니다.** 현재도 독립 Review 설정 파일을 운용하거나 이전 파일을 마이그레이션하는 경로가 없다는 것이 확인 범위입니다. Sampling 선택 코드가 남은 것과 구분합니다.

레시피 부가 폴더는 [접두사 기준 소유권](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.File/JHMI/CJhmiRecipeFile.cs#L1284-L1293)을 사용하므로 A와A_B처럼 이름이 겹치는 경우를 시험해야 합니다. 또 [복사 후 로그 호출](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/8872e4ed5176b5d8a39f1711af9501f6fac94deb/Drilling.File/JHMI/CJhmiRecipeFile.cs#L1330-L1353)이 실패하면 파일은 생성됐는데 호출자가 오류를 받을 수 있습니다. 실제 복사 사고나 로그 장애를 재현한 것은 아니며 조건부 예외 처리 검수 항목입니다.

## 권장 처리 순서

1. Log 소스와 ignore 범위를 복구하고 전체 새 빌드를 성공시킵니다.
2. 의도한 MELSEC 개선·회귀 프로젝트를 되살릴지 결정하고 수신/표시를 분리해 재시험합니다.
3. 생산 Recipe·보정 파일·시뮬레이션 기본값을 정리하고 승인 gate를 확인합니다.
4. 0선 포인트별/단일 세션의 자료 버전·실기 선대기/본검사·일반IOF·Vision 단위 계약을 확정합니다.
5. PTW 인계/재시작·ATT/TPM·HEAVY·Product 상태를 검증한 뒤 승인된 환경에서 배포합니다.
