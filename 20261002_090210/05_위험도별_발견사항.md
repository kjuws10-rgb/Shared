# 05. 위험도별 발견사항

위험도는 “실장비 좌표·Laser·검사 결과에 직접 영향을 주는가”와 “문제가 생겼을 때 자동으로 잡히는가”를 기준으로 정했습니다.

## 한눈에 보는 우선순위

| 위험도 | 항목 | 현재 판단 |
|---|---|---|
| 매우 높음 | H01 목표 좌표 X/Y가 바뀌고 마지막 점이 가공 | 실장비 적용 전 차단 필요 |
| 매우 높음 | H01~H08 모두 활성화, Head 간 전역 좌표 결합 | 전체 Head 무발진 검증 필요 |
| 매우 높음 | `AUTO_INSPECTION_USE=ON`이나 Station Review는 예약 로그뿐 | 완료로 오인 금지 |
| 높음 | Encoder 축 `GY_1→GX_1` | 축/배선/Feedback 방향 확인 필요 |
| 높음 | Hole/Corner Masking 형상과 값 동시 변경 | 전체 미가공 목록 승인 필요 |
| 높음 | MELSEC 주소가 Placeholder, Review 이동 전송 TODO | 실제 운전용으로 사용 금지 |

## 매우 높음

### R1. H01이 명시된 정상 좌표를 만들지 않는다

최신 H01 첫 점은 `(-501.0125,-28.4875)`, 마지막은 `(-1344.2125,44.4125)`입니다. 목표는 각각 `(-28.4875,-501.0125)`, `(44.4125,-1344.2125)`입니다. 마지막 레이저도 목표는 OFF인데 최신 결과는 ON입니다.

영향:

- 잘못된 축 방향으로 이동 가능
- 의도한 유리 위치가 아닌 곳에 발진 가능
- 끝점 보호 영역 가공 가능

권장:

1. 실제 Laser를 끕니다.
2. H01 단독으로 Flip/Encoder/Start Delay를 복원해 좌표를 비교합니다.
3. Masking은 별도 검토하여 마지막뿐 아니라 전체 OFF 목록을 승인합니다.
4. 첫 6점·마지막 6점 자동 회귀 검사를 통과하기 전 발진하지 않습니다.

근거: [Setting.csv L52-L97](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a25ba3cdfd70cff5d78172d13ec957318704b1e1/Config/Setting/Setting.csv#L52-L97), [test0929.csv L30-L79](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a25ba3cdfd70cff5d78172d13ec957318704b1e1/Config/RECIPE/test0929.csv#L30-L79).

### R2. 8개 Head 활성화가 H01 좌표에도 영향을 준다

H02~H08을 모두 켠 결과 전체 점 수가 2,380개에서 20,740개로 늘었습니다. 더 중요한 점은 활성 Head 범위와 `HeadGapY=380`이 전역 시작 기준에 들어가 H01 위치도 바꾼다는 것입니다.

영향:

- Head를 추가로 켜는 설정 변경이 이미 검증한 H01 좌표를 무효화
- Head별 Field 경계·중복·누락 가능
- 8개 Automation Task가 한꺼번에 생성/실행될 위험

권장:

- Head 하나씩 추가하는 단계별 시험
- 매 단계 H01 첫/마지막 좌표 고정 검사
- 전체 Head Field coverage와 중복 좌표 검사
- Laser OFF 상태에서 Encoder 대기 완료 확인

### R3. 자동 검사 ON 표시와 실제 동작이 다르다

설정은 `AUTO_INSPECTION_USE=ON`이지만 Station의 `RunReviewStep`은 “나중에 연결” 로그만 남깁니다. 작업자는 공정 Sequence가 Review 단계를 통과했다는 화면만 보고 검사가 끝났다고 오인할 수 있습니다.

영향:

- 미검사 제품을 검사 완료로 판단
- Product 진행 상태와 물리 검사 상태 불일치

권장:

- 실제 연결 전 `AUTO_INSPECTION_USE=OFF` 운영 검토
- 또는 Review 미연결 상태를 명확한 NG/Interlock로 표시
- Product 완료 조건에 실제 ReviewResult 존재·측정 성공을 확인하는 검증 추가 검토

근거: [CStationProcess.cs L1350-L1354](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a25ba3cdfd70cff5d78172d13ec957318704b1e1/Drilling.Common/Station/CStationProcess.cs#L1350-L1354).

## 높음

### R4. Encoder 축 변경

H01 Encoder 축이 `GY_1`에서 `GX_1`로 바뀌었습니다. Script의 `wait(AuxiliaryFeedback...)` 조건은 가공 위치마다 실행되므로 잘못된 축은 단순 로그 오류가 아닙니다.

확인 항목:

- 실제 Encoder가 어느 축에 연결됐는지
- `CountsPerUnit`와 `H01_ENCODER_SCALE`의 단위
- 음수 진행에서 비교 연산 방향이 맞는지
- `H01_ENCODER_FEEDBACK_FLIP`과 실제 증가/감소 방향

### R5. Masking 의미가 동시에 여러 곳에서 바뀌었다

알고리즘이 직사각형 Corner 방식으로 바뀐 시점에 Recipe 값도 Hole 3 제거, Corner 2 활성화로 바뀌었습니다. 코드 변화와 데이터 변화가 동시에 일어나 원인 분리가 어렵습니다.

특히 오른쪽 아래 Corner X를 2.75로 시험하면 목표 마지막 점은 OFF가 되지만 다른 4점도 추가 OFF가 됩니다. 마지막 한 점만 보고 승인하면 안 됩니다.

권장 검증 산출물:

- 전체 `가공/미가공` 좌표 CSV Diff
- Hole별, Corner별로 왜 OFF인지 Reason 포함 목록
- 네 모서리 확대 Plot 또는 표
- 과거 Hole 3의 설계 의도 확인

### R6. MELSEC/Review 이동은 Prototype 수준

새 주소 29개는 설명 자체가 `placeholder`이며 Review 이동 코드는 실제 전송하지 않습니다. Monitor가 보여주는 여섯 Scenario도 상태 머신이 아니라 현재 Bit 표시입니다.

권장:

- PLC 담당자 승인 주소표 없이는 실제 모드 금지
- ABLE→START→COMPLETE 순서, Timeout, Reset, Abort 상태 정의
- Stage/Vision 실제 위치 피드백 확인 후 측정
- Simulation 결과 파일과 실측 파일에 분명한 표식 유지

근거: [JHMI_MELSEC_MAP.csv L39-L67](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a25ba3cdfd70cff5d78172d13ec957318704b1e1/Config/JHMI_MELSEC_MAP.csv#L39-L67), [CReviewManager.cs L1907-L1953](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a25ba3cdfd70cff5d78172d13ec957318704b1e1/Drilling.Common/Review/CReviewManager.cs#L1907-L1953).

### R7. Model 2~5를 선택하면 점 수가 예상보다 크게 늘 수 있다

`test0929`의 Model 2~5 Pixel이 144×256에서 864×512로 바뀌었습니다. 지금은 모든 Cell이 Model 1이라 잠자지만, UI에서 Cell Model Type을 바꾸면 즉시 큰 Pattern이 계산됩니다. Chess가 점 수를 줄여도 원본 격자가 커졌기 때문에 Script 길이와 Review 후보가 급증할 수 있습니다.

권장:

- Model별 단일 Cell 점 수 표를 UI/검증 문서에 고정
- Recipe Save 전에 예상 Shot/Beam/Script line 수 표시
- Buffer 1,000 lines, Queue 100, Timeout 600,000 ms와 함께 성능 시험

## 중간

### R8. 현장 외부 Recipe의 새 Model 키 누락

Repository에 있는 Recipe 6개는 이관됐습니다. 하지만 백업, 네트워크 폴더, 작업자가 복사한 Recipe는 검사되지 않았습니다.

권장 필수 키:

```text
MODEL1_PITCH ... MODEL5_PITCH
MODEL1_CHESS ... MODEL5_CHESS
MODEL1_CHESS_TYPE ... MODEL5_CHESS_TYPE
```

JHMI 정상 Load는 기본값을 보충하지만, 직접 Dictionary 경로에서는 기본 Pitch 1이 적용될 수 있습니다. 배포 전 실제 Recipe 디렉터리를 일괄 검사하는 것이 안전합니다.

### R9. Shot Offset 정리 로직이 구형 `PITCH`를 읽는다

실행 계산은 Model별 Pitch로 바뀌었는데 Recipe Save 중 Shot Override 범위 계산은 아직 `PITCH`를 읽습니다. 새 Recipe에서 0이 되어 범위를 “정의 안 됨”으로 처리하고, 범위 밖 과거 Offset을 그대로 저장할 가능성이 있습니다.

영향:

- Recipe 파일 비대화
- 삭제된 Shot의 Review Offset 잔존
- Model/Pitch 변경 후 과거 보정 키 혼재

근거: [CJhmiRecipeFile.cs L537-L577](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/a25ba3cdfd70cff5d78172d13ec957318704b1e1/Drilling.File/JHMI/CJhmiRecipeFile.cs#L537-L577).

### R10. 좌표 CSV 열 이름 호환성

`ProductId`가 `GlassId`로 바뀌고 `가공여부`가 추가됐습니다. 열 이름으로 값을 찾는 Parser는 고칠 수 있지만, 열 순서를 고정 인덱스로 읽는 외부 프로그램은 값이 밀릴 수 있습니다.

권장:

- MES/분석기/Excel Macro/수집 Script의 Header 기반 여부 확인
- 과거·현재 CSV 두 파일로 호환성 시험
- Schema version 열 추가 검토

## 낮음

### R11. JHMI 표시 순서 중복

각 Model의 `CHESS`와 `CHESS_TYPE`이 같은 DisplayOrder를 공유합니다: 522, 524, 526, 528, 530. 현재 정렬 구현이 안정적이면 우연히 원하는 순서가 나오지만, 정렬/플랫폼 변경 시 위치가 바뀔 수 있습니다.

### R12. 전체 Solution 회귀 프로젝트 누락

UI 프로젝트는 빌드되지만 `Drilling.sln`은 Repository에 없는 두 Regression 프로젝트를 참조하여 실패합니다. 즉 전체 회귀 Test를 실행했다고 말할 수 없습니다.

### R13. 생성물·IDE 캐시가 Commit에 포함됨

307개 생성물이 실제 34개 변경을 가립니다. 기능 오류는 아니지만 Review와 Merge 품질을 떨어뜨리고, 빌드 환경별 차이를 계속 만들 수 있습니다.

권장:

- `.gitignore`와 추적 대상 재검토
- 소스 Commit과 Build 산출물 분리
