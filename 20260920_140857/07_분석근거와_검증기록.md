## 2. 원본 보존 조치

사용자 요청에 따라 원본 저장소는 분석만 했습니다.

- 기존 작업 폴더를 재사용하지 않고 별도 Clone을 만들었습니다.
- 분석 Clone의 `origin` Push URL을 `DISABLED`로 바꿨습니다.
- 분석 전후 `git status --short`가 비어 있음을 확인했습니다.
- 빌드로 생길 수 있는 파일도 원본 분석 Clone에 쓰지 않도록 별도 검증 Clone에서만 빌드했습니다.
- 원본 저장소에는 Commit, Push, 파일 수정, 파일 추가를 하지 않았습니다.

```text
원본 GitHub
  ├─ 읽기 전용 분석 Clone ── 소스/CSV/XAML 추적
  └─ 별도 빌드 검증 Clone ── bin/obj 생성 허용

Shared GitHub
  └─ 20260920_140857 ── 이번 분석 문서만 추가
```

## 3. 조사 방법

### 3.1 저장소 전체 구조 조사

다음 항목을 확인했습니다.

- 솔루션과 프로젝트 참조 관계
- 실제 C#·XAML·CSV 파일 수
- `bin`, `obj`, `.vs` 등 생성 파일 추적 여부
- 설정 루트와 프로그램 시작 순서
- Manager, Adapter, Process Step 구성
- Recipe/Review/Correction 관련 클래스와 화면 이벤트 연결

### 3.2 문자열과 호출 관계 추적

파일명만 보고 판단하지 않고 아래 순서로 연결을 따라갔습니다.

```text
화면 버튼/Command
  → Manager 공개 메서드
  → 계획 생성기/파일 로더
  → 좌표·규칙 계산
  → 장비 Adapter 또는 결과 저장
  → 다시 화면/Product/보정으로 전달
```

특히 다음 이름을 저장소 전체에서 검색해 실제 참조 여부를 확인했습니다.

- `REVIEW_RULE_FILE`
- `JHMI_REVIEW_RULE`
- `ReviewRule`
- `CreatePlan`, `BuildHolePoints`, `MeasureVision`
- `CShotCoordinatePlanBuilder`
- `ReviewResult`, `HoleKey`, `RecipeOffset`, `ReviewOffset`
- `MoveStageToScanStart`

### 3.3 실제 CSV 파싱과 수치 확인

`Config/JHMI_RCP.csv`, `Config/RECIPE/*.csv`, Model Pixel 파일을 실제로 읽어 다음을 집계했습니다.

- JHMI 정의의 TAB별 행 수
- 각 예제 레시피의 행 수와 Cell 수
- Cell별 Model 연결
- Model별 Pixel X/Y 크기
- Pitch로 나눈 Shot Group 수
- Split 설정에 따른 Beam 수

수치는 단순 파일 줄 수가 아니라, 코드가 사용하는 필드와 같은 의미로 재계산해 서로 대조했습니다.

### 5.2 예제 레시피

`Shot Group`은 Model Pixel 크기를 Pitch로 나눈 그룹 수를 Cell별로 계산해 합한 이론값입니다. 가장자리 나머지는 현재 계산 방식처럼 제외했습니다.

| Recipe | CSV 행 | Cell | 이론 Shot Group | Split 설정 | 한 Group의 Beam |
|---|---:|---:|---:|---:|---:|
| `animotion` | 342 | 5 | 1,750 | 4 | 16 |
| `DRILL_A01` | 505 | 45 | 15,750 | 4 | 16 |
| `sample3` | 344 | 1 | 25 | 1 | 1 |
| `simple2` | 1,042 | 180 | 101,808 | 레시피 값에 따름 | 1 또는 16 |
| `wizardtest` | 1,042 | 180 | 82,404 | 레시피 값에 따름 | 1 또는 16 |

### 5.3 확인된 Model Pixel 크기

| 적용 예 | Model | Pixel X × Y |
|---|---|---:|
| `DRILL_A01`, `animotion` | 사용 Model | 144 × 256 |
| `sample3` | 사용 Model | 5 × 5 |
| `simple2`, `wizardtest` | M1 | 144 × 256 |
| 〃 | M2 | 256 × 144 |
| 〃 | M3 | 288 × 512 |
| 〃 | M4 | 144 × 256 |
| 〃 | M5 | 144 × 256 |

이 표가 “Cell마다 Hole 수가 같다”는 가정을 검토하는 근거입니다. M1~M5의 크기가 다르므로 평균 인덱스 방식은 혼합 Model 레시피에서 안전하지 않습니다.

> 주의: 표의 이론 Shot Group은 기하학적 기본 개수입니다. 실제 실행 점은 Model 마스크, 둥근 모서리, CHESS 규칙, Head 활성 상태, 좌표 범위 검증 등에 의해 줄어들 수 있습니다.

## 6. 빌드 검증

### 6.1 UI 프로젝트 단독 빌드

별도 검증 Clone에서 Release 빌드를 실행했습니다.

```text
대상: Drilling.UI 프로젝트
결과: 성공
오류: 0
경고: 2
```

확인된 핵심 경고는 `CRootView`의 메뉴 접근 코드 중 일부가 도달 불가능하다는 내용입니다. 메서드 앞부분의 무조건 `true` 반환과 연결됩니다.

### 6.2 솔루션 전체 빌드

```text
대상: 전체 Solution
결과: 실패
주요 원인: 솔루션이 참조하는 아래 프로젝트 파일이 저장소에 없음
  - Drilling.Regression.csproj
  - Drilling.UI.Regression.csproj
```

따라서 “제품 프로젝트가 컴파일되지 않는다”는 뜻은 아닙니다. UI 프로젝트는 단독으로 성공했고, 전체 솔루션은 누락된 회귀 프로젝트 참조 때문에 실패한 것입니다.

## 7. 핵심 결론의 근거 연결표

| 결론 | 확인한 근거 종류 |
|---|---|
| 레시피가 JHMI 정의와 실제 값 CSV의 2층 구조임 | Recipe Record, JHMI Loader, Recipe File, Manager 호출 관계 |
| 동적 Cell/Offset 키가 저장 시 합쳐짐 | Recipe 로더·저장기와 Cell/Shot Offset 생성 코드 |
| Process와 Review가 같은 Shot 좌표 계획을 재사용함 | `CShotCoordinatePlanBuilder` 호출 관계와 `(CellNo, ShotGroupNo)` 매핑 |
| Review Hole은 원본 Pixel 하나가 아니라 Shot Group임 | Hole 생성과 Group 번호 전달 흐름 |
| Split 4는 16 Beam을 뜻함 | X/Y 각각 4분할하는 Beam 격자 계산 |
| 실제 Review는 메인 `INSPECTION` 단계에서 실행되지 않음 | Process Step의 `RunReviewStep`과 Review UI 시작 경로 비교 |
| Vision 결과가 임시값임 | `MeasureVision`의 미구현 송수신과 임시 측정 생성 호출 |
| 일부 규칙 파일은 현재 실행 경로에서 읽히지 않음 | 파일 존재 확인 + C#/XAML 전체 참조 검색 |
| 혼합 Model에서 평균 Hole 인덱스 위험이 있음 | Model별 크기 비교 + `total/cellCount` 기반 접근 코드 |
| 보정은 Review 오차를 좌표 변환해 Recipe Offset에 더함 | Correction Load→Calculate→Apply→Save 호출 추적 |
| 중복 보정 방지는 실행 중 메모리 한정임 | 적용 경로 집합의 수명과 영구 저장 부재 확인 |

## 8. 이번 분석의 한계

이번 결과는 코드와 저장소 데이터에 대한 면밀한 **정적 분석**입니다. 다음은 실제 장비 환경 없이는 완전히 검증할 수 없습니다.

- Wonik Stage, Vision, Power Meter, PMAC, Laser의 실제 응답
- 외부 실행 파일이나 PLC가 추가로 수행하는 동작
- 고객사별 운용 절차와 레시피 작성 규칙
- 실제 장비 좌표 원점, 부호, 캘리브레이션 값의 물리적 정확성
- 장시간 운전, 동시 실행, 전원 차단 중 파일 복구
- 배포 과정에서 소스와 다른 DLL이 교체·주입되는지 여부

따라서 좌표식의 코드상 흐름은 설명할 수 있지만, 실제 가공 위치의 정밀도와 Vision 결과의 물리적 타당성은 장비 로그 및 기준 시편으로 별도 검증해야 합니다.

## 9. 재검증할 때의 권장 체크리스트

1. 분석 기준 Commit을 기록합니다.
2. 원본과 분리된 Clone에서 빌드합니다.
3. 대표 레시피별로 예상 Group/Beam 수를 미리 계산합니다.
4. 프로그램이 만든 Plan의 Cell/Head/Group별 수와 비교합니다.
5. Head 하나씩 비활성화해 누락 수를 확인합니다.
6. 서로 다른 Pixel 크기의 Model을 한 레시피에 섞어 Review 점을 확인합니다.
7. Simulation/LIVE 각각에서 Vision 결과 원천을 로그로 증명합니다.
8. 같은 Review 파일을 재시작 전후 두 번 적용해 차단 여부를 확인합니다.
9. 보정 전후 Recipe CSV와 감사 기록을 비교합니다.
10. 같은 초에 결과를 두 번 저장해 파일 충돌 여부를 확인합니다.
