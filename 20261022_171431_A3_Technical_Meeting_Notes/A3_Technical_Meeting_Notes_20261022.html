02

시뮬레이션·인터페이스 평가 범위

실제 설비가 없는 환경에서는 신호를 주고받으며 시퀀스가 정상 전이되는지를 우선 확인한다.

구분미팅 정리평가할 내용
우선 범위Pre-align·Align·DoReady·Process·Review 등에서 관계 PC/PLC와 요청·응답을 주고받는 흐름. 가공SW ↔ Stage는 Melsec, 가공SW ↔ Vision은 TCP/IP 소켓이라는 기존 구분을 따른다.정상 순서, 대기 조건, 누락·중복 응답, 완료 후 신호 정리.
수동 동작수동 Online 요청과 단동 기능도 필요한 인터페이스를 확인한다.수동 요청 → 상대 완료 응답 → 다음 기능 허용.
보호윈도Shift·교체까지 연동되면 좋지만, 최소한 요청/완료 핸드셰이크를 준비하는 방향.위치 모델 없이 논리적인 요청·진행·완료 응답을 재현할 범위 합의.
재현 부담 축소축마다 위치 명령과 서보 Position Complete를 모두 흉내 내는 것은 공수가 크다. 필요한 논리 응답에 집중한다.어떤 응답을 모의로 주는지 평가표에 표시.
평가의 경계실제 서보·위치 정확도·스캐너 출력·카메라 촬영 성능은 별도 실기 평가 대상.인터페이스 PASS와 물리 동작 PASS를 구분.
산출물에 남길 것

시나리오별 시작 조건, 요청/응답, 완료 조건, 타임아웃/이상 응답 처리와 평가 결과를 기록한다. 모의 COMPLETE를 받았다는 사실을 실제 축 도착 확인으로 사용하지 않는다.

MOF 버튼 하나가 Script 실행·실행 확인·Stage 요청까지 수행하는지, 버튼을 분리하는지는 실제 구현을 확인한다. 전사에서 Ready 위치로 언급한 “4800”은 장비 예시이며, 단위와 좌표 기준이 확인되지 않았다.

04

AUX 초기화와 MOF 결합 순서

MOF 결합 뒤에 엔코더 값을 초기화하면, 스캐너가 값의 변화를 이동으로 해석할 수 있다는 설명이 있었다.

  1. Process Ready
    실제 도착·정지
  2. AUX 값 초기화
    대상/API 확인
  3. 안정화 대기
    설정값 관리
  4. MOF 결합
    이후 안정화 대기
  5. 준비 상태 확인
    가공 이동 요청
항목정리 내용
순서AUX 초기화 → 대기 → MOF 결합 → 대기를 우선 적용 방향으로 정리. 결합 전에 초기화하는 이유를 Script 주석·시나리오에 남긴다.
명령 확인전사상 “옥수/옥스”는 AUX 또는 보조축 피드백을 뜻하는 것으로 추정된다. 실제 초기화 대상·명령·장치 API는 확인해야 한다.
중복 방지초기화가 Script 안에도 있는지 확인한다. Script 외부에서 초기화한 뒤 내부에서 결합 후 다시 초기화하는 문제가 없는지 검토한다.
대기 시간초기화 후 약 0.1초, 결합 후 약 1초가 경험값으로 언급되었다. 확정 규격이 아니며 실기에서 조정할 설정값이다.
구분AUX 피드백 초기화는 Default Offset을 맞추는 작업과 구분한다. “MOF Zero Set”에 포함되는 세부 동작도 명확히 한다.
05

0선 좌표·Melsec·IOF 요청·PEG 활성화

좌표를 준비하는 일과 Trigger를 실제로 발생 가능한 상태로 만드는 일은 서로 다른 사건이다.

계획

① 좌표 생성

레시피와 옵션으로 내부 계획 준비.

데이터

② Melsec 기록

어떤 영역에 언제 쓰는지 합의.

명령

③ IOF 요청

좌표 쓰기와 별도 요청을 구분.

Stage 처리

④ 읽기·ACS·PEG

정해진 정지 위치에서 활성화.

구분현재 기준과 회의 논의문서 반영 방향
기존 사용자 기준Process ABLE 조건 성립 + Process Ready 실제 도착·정지 확인 → Melsec에 PEG 위치 쓰기 → Stage ACS 반영. 이동 중 활성 PEG 정보 쓰기는 하지 않는다.기존 시나리오의 기준을 유지한다.
이번 회의의 선기록 의견DoReady에서 좌표를 미리 써 두고, Stage가 별도 요청을 받았을 때 읽어 PEG를 생성할 수 있다는 의견이 있었다.변경 제안으로 남긴다. 내부 계획/비활성 버퍼와 활성 PEG 영역의 분리 여부를 확인하기 전 기존 기준을 대체하지 않는다.
빠져 있던 인터페이스좌표 데이터와 별도로 IOF를 수행/적용하라는 요청이 필요하다는 논의.요청 신호명·주소·Stage의 읽기 시점·PEG 생성 시점을 통신 계약에 추가한다. 전사에 확정 주소는 없다.
공유 좌표 영역0선방어와 IOF가 같은 좌표 영역을 쓰면 시점이 꼬일 수 있다는 지적. 영역 분리도 제안되었다.영역 분리 또는 명시적인 계획 식별·적용 조건을 검토한다. 신규 주소를 임의 지정하지 않는다.
0선방어 OFF기존 기준상 Stage가 0선 좌표를 읽거나 이전 Trigger를 사용하면 안 된다.사용 여부를 우선 분기하고 이전 데이터가 남아도 비활성 상태를 확인한다.
첫 Review X 선행 이동첫 촬영 전에 충분히 도착하도록 DoReady/레시피 준비 구간으로 앞당기는 방향.요청·실제 도착 확인을 Stage와 맞춘다. 첫 X 이동과 PEG 활성화 시점을 한 사건으로 묶지 않는다.
다음 회의에서 결정할 문장

“데이터를 쓰면 바로 PEG가 생성되는가, 별도 요청을 받아야 생성되는가?”를 먼저 확정해야 한다. 그 답에 따라 선기록 허용 영역과 활성화 시점을 정한다. 이번 문서는 이동 중 활성 PEG 기록을 허용한 변경 지시가 아니다.

06

Full Review IOF: 개수 확인과 결과 확인

촬영 개수가 맞는지와, 각 마크를 정상적으로 찾았는지는 별도 판정이다. 1002 ACK의 의미를 명확히 해야 한다.

  1. Glass·Cell·LINE·X포인트
    기대 개수 계획
  2. 시퀀스 시작
    1900 Keep-Alive
  3. 1001 FLYING READY
    Vision 준비·ACK
  4. Stage X Flying
    HW Trigger·Grab
  5. 라인 끝 이동 완료
    1002·ACK
  6. 1003 결과 요청/회신
    개수·측정 유효성

1900은 각 측정 시퀀스 시작에 1회. 1001·1002·1003마다 반복하는 의미가 아니다. 명령 번호는 기존 A3 IOF 자료와 전사 용어를 맞춰 표기했다.

구분회의에서 나온 내용정리 결론
초반의 가정1002 ACK를 받으면 요청한 Grab 개수가 정상이고 다음 위치로 이동할 수 있다는 설명.이 가정은 뒤의 Vision 설명과 구분해야 한다.
Vision 측 현행 설명1002 ACK는 Move Done 수신·이미지 수신 큐 종료 성격. 개수/측정 결과는 결과 요청 단계에서 확인한다는 설명.현재 ACK가 개수 정상까지 보증한다고 단정할 수 없다.
개선 방향Grab 개수를 먼저 확인하고 다르면 조기에 알려 달라는 요청.개수 판정을 1002 응답에 포함할지, 별도 상태로 보낼지 확정 필요.
개수 오류 예시10개 요청에 9개 또는 11개 수신. 어느 위치에서 누락/추가됐는지 모를 수 있다.해당 시도의 데이터를 정상 보정에 사용하지 않는다. 같은 라인 재측정/보류 정책과 오류 응답을 확정한다.
측정 실패개수는 같아도 Mark Find 실패가 있을 수 있다.개수 이상 처리와 별개로, 측정 실패 시 즉시 재측정 옵션을 둔다.
데이터 보관개수 오류 데이터를 보정에 쓰지 않는 것과 로그·이미지를 지우는 것은 다르다.진단용 원본은 보관 정책에 따라 유지하고 정상 결과와 분리한다.

다음 라인으로 이동해도 되는 조건

조건이동·결과 처리 방향
개수 확인 실패동일 라인 재측정/보류를 먼저 판단한다. 다음 라인의 정상 촬영으로 넘기지 않는다.
개수 정상 + 즉시 재측정 사용1003 측정 결과까지 확인한 뒤 다음 라인으로 이동한다. 실패하면 현재 끝점에서 같은 라인을 재측정한다.
개수 정상 + 즉시 재측정 미사용다음 위치 이동과 결과 처리를 겹치는 방안을 검토할 수 있다. 유효하지 않은 결과를 정상 보정에 쓰면 안 된다.
현행 ACK에 개수 정보 없음1002 ACK만으로 위의 “개수 정상” 조건을 충족할 수 없다. 기존 결과 대기 기준을 유지하거나 명시적 개수 확인 응답을 추가해야 한다.
통신 계약에서 남은 결정

기대/실제 Grab 수, 개수 판정, 측정 판정, 오류 코드, 타임아웃과 재시도 한도를 정의한다. ACK/NACK의 구체 필드·번호는 회의에서 확정되지 않았다. 현재 Full Review 문서의 결과 대기 기준을 조건부 Overlap으로 바꾸는 작업도 별도 결정 대상이다.

Top Powermeter: 안정 구간 측정과 보정

초기 응답이 안정되기 전 구간을 제외하고, 유효한 측정 구간의 값을 헤드별로 모아 평균을 내는 방향이다.

회의 설명을 옮긴 개념 그래프이며 실제 장비의 측정 데이터가 아니다.

항목정리 내용
측정 계획해당 레시피/파일을 로드한다. 비어 있는 값·중복·이전 측정값과 현재 결과를 구분하는 조건이 필요하다.
설정 항목시작 안정화 시간, 측정 시간, 수집 주기, 반복 사이클, 필요 시 냉각 시간을 관리한다. 각 조건의 레시피/장비 설정 소속도 정한다.
헤드별 평균각 헤드의 유효 샘플 합과 수를 따로 관리해 평균한다. 헤드별 수신 누락·시간 초과·유효 상태도 함께 관리한다.
시간 vs 횟수측정 시간 동안 계속 수집해 평균한 기존 방식과, 지정 횟수로 평균하는 방식이 논의되었다. 필요한 안정 구간과 유효 샘플 수를 기준으로 선택한다.
새 측정값 확인함수 호출 횟수가 매우 많다는 경험이 언급되었다. 호출 횟수 = 독립된 신규 계측 샘플 수라고 가정하면 안 된다. 응답 갱신 주기·샘플 번호/시각·중복 읽기를 확인한다.
메이커 확인레이저 Power 조건에 맞는 초기 제외 시간·유효 측정 시간·냉각 시간과 계측기 데이터 갱신 주기를 확인한다. 통신 방식·채널·응답 정의도 계약에 명시한다.
완료 판정현재 측정과 필요한 보정의 결과를 판정한 뒤 COMPLETE를 교환한다. 샘플 부족이나 통신 실패를 이전 값으로 정상 처리하지 않는다.

Attenuator 각도: 이전 변화량으로 다음 값을 예측

회의의 설명 예시 · Power 단위는 실제 계측기와 확인22° → 140, 23° → 145 ⇒ 기울기 k = 5 Power 단위/°

현재 23°·145에서 목표 175라면: 23 + (175 − 145) ÷ 5 = 29°

국소적으로 선형이라고 가정한 예상값이다. 이동 후 실제 Power를 다시 측정해야 한다.

구분반영 방향
회의 방향이전의 각도 변화와 Power 변화를 저장·갱신해 다음 이동량을 예측한다.
가중치새 보호윈도/사용한 보호윈도에서 반응이 다르다는 경험에 따라 가중치를 조절했다는 설명. 1.7·1.2·0.7은 경험값 예시이며 보편 권장값이 아니다.
미결 사항기울기 갱신 기준, 가중치를 곱할지 나눌지와 적용 위치, 각도/사용률 제한, 최대 보정 횟수와 미수렴 처리는 확정되지 않았다.
개발 검토 제안기울기가 너무 작거나 부호가 이상한 경우, 비선형 구간에서는 예측 이동량을 제한하거나 기존 측정 기반 탐색으로 전환하는 조건을 둔다. 계산·이동·재측정으로 검증한다.

윈도 식별자·현재 사용 매수·허용 한계·교체 대기 상태·마지막 동기화 정보를 보존하고, Reset/재시작 뒤 다시 대조한다. 하나의 기준 카운터를 정하고 상대 PC는 변경 이벤트와 확인 절차로 동기화한다. 구체 필드와 저장 방식은 후속 설계 대상이다.
