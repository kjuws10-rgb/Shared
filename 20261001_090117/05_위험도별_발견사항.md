## 치명적 — Review 장비 이동 미연결

### 코드에서 확인한 사실

1. `MoveStageY`는 명령 문자열을 만들지만 `_ = command`로 버립니다.
2. `MoveVisionX`도 같은 방식이며 실제 MELSEC 전송이 없습니다.
3. IOF 시작/완료 이동도 위 두 함수를 사용합니다.
4. 반면 Vision은 `MARK_FIND_SINGLE` 또는 Line 명령을 실제 통신 경로로 보낼 수 있습니다.
5. `JHMI_INTERFACE.csv`의 Vision `SIMUL`은 0입니다.

근거: [Stage 이동 TODO](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/6b19d7aaf0de81271468ab7dac0fa15493172f38/Drilling.Common/Review/CReviewManager.cs#L2054-L2073), [Vision X 이동 TODO](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/6b19d7aaf0de81271468ab7dac0fa15493172f38/Drilling.Common/Review/CReviewManager.cs#L2075-L2101), [실측 호출](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/6b19d7aaf0de81271468ab7dac0fa15493172f38/Drilling.Common/Review/CReviewManager.cs#L2103-L2150), [Vision 실모드 설정](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/6b19d7aaf0de81271468ab7dac0fa15493172f38/Config/JHMI_INTERFACE.csv#L1-L3).

### 가능한 결과

- 장비가 목표 위치에 가지 않았는데 Vision 측정이 실행됨.
- 다른 Shot의 오차를 현재 Shot의 결과로 저장함.
- 잘못된 결과가 Correction Offset으로 Recipe에 반영됨.
- 다음 가공 전체 좌표가 잘못 보정됨.

### 권장 조치

1. MELSEC 주소와 Request/Ack/Complete/Error Handshake를 확정.
2. 실제 위치 피드백이 허용 오차 안에 들어왔을 때만 Vision 측정을 허용.
3. 연결 전에는 `SIMUL=0` Review Start를 코드와 UI 양쪽에서 차단.
4. P2P 한 점 Dry-run → 여러 점 → IOF 순서로 승인 시험.

## 높음 — 자동 INSPECTION은 실제 Review가 아니다

`RunInspectionStep`은 `RunReviewStep`을 호출하지만 현재 구현은 예약 로그만 남깁니다. `AUTO_INSPECTION_USE=ON`만으로 자동 Review가 실행된다고 판단하면 안 됩니다.

근거: [CStationProcess.cs L860-L863](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/6b19d7aaf0de81271468ab7dac0fa15493172f38/Drilling.Common/Station/CStationProcess.cs#L860-L863), [L1350-L1354](https://github.com/kjuws10-rgb/A3_LD_Process_SW_IPS/blob/6b19d7aaf0de81271468ab7dac0fa15493172f38/Drilling.Common/Station/CStationProcess.cs#L1350-L1354).

권장: 자동 공정 완료 조건에 Review Result 경로, 완료 상태, 측정 수를 명시하고 실제 Review Manager 완료 신호를 연결해야 합니다.

## 높음 — Recipe 내용 버전이 Result에 없다

ReviewResult에는 `RECIPE_ID`는 있지만 Recipe 파일 내용의 Hash 또는 Version은 없습니다. Correction은 Result를 읽은 시점의 현재 Recipe로 전체 Plan을 다시 만듭니다.

현재도 ShotKey와 Head가 맞지 않으면 오류를 낼 수 있지만 다음 경우는 탐지하기 어렵습니다.

- Recipe ID는 같고 Cell 위치만 조금 변경
- Masking 값만 변경
- Flip/HeadGap/Scan Delay가 변경
- ShotKey 목록은 같지만 좌표가 변경

권장 저장 필드:

```text
RECIPE_CONTENT_SHA256
SETTING_COORDINATE_SHA256
SOURCE_COMMIT
PLAN_VERSION
```

Correction Apply 전에 현재 값과 Result 값을 반드시 비교하고 불일치 시 사용자 승인 없이 저장하지 않아야 합니다.

## 높음 — Masking 호환성 변경

### 변경 1: Hole 4/5 삭제

최대 5개에서 3개로 줄었습니다. 외부/구형 Recipe에 Hole 4/5가 있어도 최신 판정은 읽지 않습니다.

### 변경 2: 중심점 포함에서 면적 교차로 변경

경계 주변의 가공 수가 달라질 수 있습니다. 이는 안전 측면에서는 보수적이지만, 과거 생산 좌표와 결과가 달라질 수 있습니다.

### 변경 3: Round 이름과 실제 의미 차이

키 이름에는 `ROUND`가 남아 있지만 실제 계산은 직사각형 Edge Offset입니다. 운영자가 “둥근 모서리 반경”으로 이해하면 설정 오류가 날 수 있습니다.

권장:

- 배포 대상 모든 Recipe의 Hole 4/5 및 Radius 사용 여부 검색
- 이전/이후 Mask 결과 수와 좌표를 자동 비교
- UI 이름을 `EDGE_OFFSET`처럼 실제 의미에 맞게 변경하거나 도움말 강화

## 중간 — Product Checkpoint와 재개 조건

권장: Checkpoint에도 Plan Hash와 Review Setting 파일 Hash를 저장합니다.

## 중간 — Git 생성 산출물 혼입

424개 변경 파일 중 약 377개가 `.vs`, `bin`, `obj` 계열입니다.

영향:

- 실제 코드 리뷰가 어려워짐
- 개발자 환경 경로·캐시가 저장소에 남을 수 있음
- Merge 충돌과 저장소 용량 증가
- 오래된 DLL과 최신 소스가 혼재할 가능성

권장: 팀 확인 후 `.gitignore`에 생성 경로를 추가하고 추적 중인 산출물을 별도 정리합니다. 이 분석에서는 원본을 수정하지 않았습니다.

권장: 누락 프로젝트를 복원하거나 Solution 참조를 의도에 맞게 정리하고 CI 기준을 하나로 고정합니다.
