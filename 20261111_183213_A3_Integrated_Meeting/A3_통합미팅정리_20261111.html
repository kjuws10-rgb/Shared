01 회의에서 정리된 핵심 방향

리뷰 측정·선택 재검사·보정을 하나의 흐름으로 연결하고, 좌표 변환과 오프셋의 적용 결과를 눈으로 확인할 수 있도록 개선한다. 현장에서는 인터넷과 자료 반출이 제한되므로, 시뮬레이션·개발 문서·재현 가능한 로그를 함께 준비한다.

구분통합된 방향남은 확인

현장 지원승인된 로그로 장애 원인을 추적하고 오프라인 개발 지원을 검증한다수집 항목·반출 범위·현장 PC 성능·재현 시험

03 기준 Shot 보정값을 선택 영역에 동일 적용

기판 표면 등의 문제로 실제 가공 흔적이 있어도 Vision이 측정하지 못하는 Shot이 많을 수 있다. 주변에서 정상 측정한 Shot 하나를 기준으로 지정하고, 사용자가 고른 대상 Shot에 그 기준 Shot의 동일한 보정값을 복사하고 싶다는 요구다.

  1. 기준으로 삼을 실측 Shot을 하나 선택한다.
  2. 적용 대상 Shot을 클릭·드래그·NG 필터로 선택한다.
  3. 기준 Shot·대상 개수·현재 보정값과 변경값을 확인한다.
  4. 선택한 영역에 같은 보정값을 반영한다.

주변 여러 점으로 값을 계산하는 Lagrange 보간과는 다른 작업이다. 회의에서는 NG·미측정 상태가 보간에 들어갈 때의 문제도 우려했다. 정리상 필요한 구분은 원시 측정 상태 보존, 실측값과 보정값 분리, 기준 Shot과 복사 대상을 추적하는 것이다. 미측정 Shot을 실측 성공으로 취급하는 사양은 확정되지 않았다.

주제회의 내용·확인할 사항

결과의 정체어느 Head·Cell·Scanner·Beam에서 언제 측정한 결과인지, AUTO에서 이미 적용된 결과인지 알 수 있어야 한다
중복 반영AUTO에서 한 번 반영한 결과를 다시 불러와 적용하는 경우 같은 보정이 중복될 가능성을 확인해야 한다
Save/ApplySAVE 순간 반영된다는 설명이 있었으나 측정 결과 저장과 보정 적용의 의미를 명확히 나눌 필요가 있다

05 선택 Shot의 좌표와 오프셋 시각 검증

선택한 Shot 하나에 대해 원본/설계 기준, Scanner 변환 기준, 각 오프셋을 반영한 위치, 최종 위치를 비교하고 싶다는 요구다. 회의에서는 Raw·Default·FirstBeam·ReviewOffset 단계별 체크박스, 다른 색과 화살표로 이동 방향을 표시하는 방안이 제시됐다. 모든 Shot을 동시에 그릴 필요는 없다는 의견이다.

검증할 항목은 Flip·축 대응(GX/GY 등), 부호·단위, 정지/MOF 좌표계, 오프셋 포함 범위와 중복 반영 여부다. 단계 표시 순서를 실제 수식의 적용 순서로 확정하지 않는다.

가공 위치 변화량을 Review 이동 좌표에 어디까지 반영할지와 Target 기준을 고정해야 하는지에 대해 발언이 엇갈렸다. Review의 촬영·이동 목표, 판정 기준, 가공 보정 좌표를 구분하여 확인하는 것이 남은 과제다. 이번 회의 정리만으로 ‘모든 보정을 Review에 동일 가산’ 또는 ‘항상 고정’으로 결정하지 않는다.

06 화면 성능과 레시피 전환

  • Monitor 진입이나 다른 메뉴에서 돌아올 때 LogViewer·CoordinateViewer의 전체 카드 재생성이 지연 원인이라는 설명이 있었다.
  • 전체 데이터를 매번 다시 그리는 방식 대신 보이는 영역과 변경된 값만 갱신하자는 요구다.
  • Design 좌표처럼 고정된 정보는 최초 로드·관련 레시피 변경 시에 준비하고 재사용하는 방향이다.
  • 레시피 변경 때는 ‘레시피를 교체 중입니다’ 같은 진행 상태를 먼저 보여 주고 완료 전 조작 범위를 제한하자는 의견이다.
  • Monitor 진입 시 무거운 탭을 자동으로 열지 않고 가벼운 기본 화면을 먼저 보이는 방안도 제시됐다. 정확한 탭 이름·성능 목표 수치는 미결이다.

07 Masking 라인 선택과 Flying Trigger 검증

Masking 구간의 촬영 제외/회피를 확인했다는 발언이 있었다. 한편 상단 Masking으로 첫 줄 샘플이 줄거나 비어 버리는 상황에서 다음 라인을 고르는 것이 보정 분포에 어떤 영향을 주는지 우려했다. 측정점을 제외하는 것, 완전히 Masking이 없는 다른 라인을 고르는 것, 이동 경로 자체를 우회하는 것을 구분해 실제 선택 좌표를 확인해야 한다.

Flying Trigger 누락 시 Vision이 Flying Move Done 응답에 카운트 불일치 NG를 주고 Process가 알람 처리하는 흐름을 시뮬레이션으로 다시 확인해 달라는 요청이다. 과거 시험을 했는지 발언이 일치하지 않아 검증 완료로 정리하지 않는다.

Vision 결과의 정상값은 기존 문서의1과 현재 설명의0이 달라, 해당 명령·결과 필드에 맞는 최신 프로토콜을 정정·공유해야 한다. Header ErrorCode·측정 판정·MELSEC ON/OFF 등 서로 다른 필드에0=OK를 일괄 적용하는 것으로 해석하지 않는다.

08 Distortion과 기준값 Range 인터페이스

항목회의 정리
두 버튼 구분현재 Process 영역과 Vision 값을 읽어 보여주는 동작, 새 Vision 값을 계산/복사하여 Process 영역에 반영하는 동작의 차이를 명확히 설명해야 한다
값의 작성 주체어떤 필드를 Stage/Vision/Process가 쓰는지, 언제 읽어야 최신인지 I/F 맵에 정리 필요
0 표시시험 중 작성되지 않은 영역이0으로 보였다는 설명이 있었다. 유효한 실측0과 미수신/미작성 상태를 구분해 확인할 필요가 있다
Range 산출Tolerance·Scale·Camera Resolution으로 Pixel Range를 계산한다는 설명이 있었다. 정확한 단위와 계산 근거를 확인해야 한다
X/Y 피팅기판이 기울어진 경우 특히 X 방향 거리·대각 성분을 어떻게 반영하는지 우려. 고정 카메라 조건에서의 피팅을 검증해야 한다
ScaleAlign 계열과 Review 계열 Scale을 별도로 적용한다는 설명이 있었다. 정확한 산식·적용 범위는 코드와 사양으로 확인 필요
문서최신 MELSEC 맵과 누락된 주소·판정 규칙을 관계사에 공유·동기화할 필요가 있다

녹취의 ‘와퍼지/와퍼즈’로 들리는 항목은 정식 I/F 명칭을 확인해야 하며 Distortion과 동일 기능으로 합치지 않는다.

09 Second Align 결과 수신과 이력

초기 Align 위치와 가공 후 디척 직전 마지막 Align 위치를 비교하여 변화를 모니터링하고 이력을 남기려는 기능이다. 이 데이터를 받아 즉시 새로운 보정을 계산한다는 합의는 없다.

Stage/Vision이 결과를 작성한 뒤 기존 완료 또는 Sequence_IO의 ON 상태를 Process가 확인하여 값을 읽고 로그를 남기는 방향이 논의됐다. 별도 ‘읽어갔다’ 응답을 늘리지 않자는 의견도 있었다. 정확한 신호명·주소·갱신 완료 의미·읽기 시점·한 사이클 식별은 미확정이다. 초기/최종 좌표와 차이를 같은 기판·카메라 기준으로 비교하는 표시도 제안됐다.

10 A1 알람 Recovery와 보호윈도우

항목요구·남은 판단
A1 동작 중 알람기판을 살릴 수 있는 복구 방안과0선 검사 동작을 논의했다. 가공 완료/미가공 범위, 재개 가능 상태, 이미 가공된 위치의 재가공 여부부터 정리해야 한다
0선 Recovery알람 후 검사를 다시 실행해도 되는지, 가공이 일부 빠진 상태에서 어떤 기준으로 반출할지 미결. 자동 재개 승인으로 해석하지 않는다
보호윈도우 매수교체 완료 시 Stage가 가진 해당 윈도우의 매수를 받아 이후 Process가 사용량을 업데이트하는 방향이 설명됐다
Shift/교체Process에서는 Shift도 교체와 유사한 완료 이벤트로 본다는 설명. 실제 적용할 매수를 무조건0으로 가정하지 않고 Stage 완료값·단위를 확인해야 한다
잘못된 교체 요청설정 횟수 오류 등으로 교체 요구가 반복될 때 취소/관리 해제 방법이 필요하다는 문제 제기. 강제 완료를 정상 교체 성공으로 간주하는 절차는 미확정
반복 교체 제한교체 후 가공을 못 하고 다시 교체하는 반복을 Retry 카운트로 제한하고 초과 시 알람을 내는 기능 추가 요청
설정 위치PPID 관련 항목을 모아 보고 싶다는 의견. Retry 한도·초기화 조건·설정 메뉴 위치는 별도 정리 필요

11 광학계 Live와 Run Enable 역할 분리

Live가 주기적으로 ON/OFF 되는데 그 순간값을 Run Enable의 조건에 직접 묶으면, 운전 상태가 정상이어도 허가 신호가 반복해서 꺼질 수 있다. 통신 생존 여부와 운전 가능 상태를 서로 다른 조건으로 취급한다.

역할회의·통화에서 정리한 동작읽는 쪽의 해석
기존 LiveMELSEC 통신이 살아 있으면 약1초마다 ON/OFF 전환. 기존 주소를 하트비트로 재사용현재값0/1보다 최근에 값이 변했는지를 확인
상대측 Run Enable알람 없음 AND 자동 모드로 운전 가능 상태를 만든다. Live의 순간값은 이 조건에서 제외최신 맵의 정상값과 수신 유효성을 확인
Process 최종 허가하트비트 변화 확인 정상 AND Run Enable 정상두 조건을 모두 만족할 때 운전 가능으로 판단
값 고정같은 값이 설정 시간 이상 유지되면 통신 이상으로 판단Run Enable이 정상값으로 남아 있어도 유효 허가로 인정하지 않음
문서 반영역할·조건을 주석으로 명시한 최신 MELSEC 맵을 공유한 뒤 반영정확한 주소·자료형·정상값을 임의로 만들지 않음

초기에 나온 ‘별도 하트비트 주소 추가’안은 통화에서 ‘기존 Live 재사용’으로 정리됐다. 두 방안을 동시에 구현해야 하는 요구로 남기지 않는다.

상황통신 판단운전 허가
Live가 계속 변화하고 Run Enable 정상변화 확인 정상허가 조건 충족
Live가 계속 변화하지만 알람 또는 수동 모드통신은 정상운전 허가 안 됨
Live가0 또는1로 고정되어 타임아웃 초과통신 이상Run Enable이 ON이어도 무효
최초 수신만 있고 변화는 미확인초기 확인 정책 필요정책 확정 필요
읽기 실패·품질 불량·재연결 직후수신/복구 정책 필요이전 캐시값으로 정상 확정하지 않기

토글 간격으로 언급된1초와 고정값을 감시하는 타임아웃은 별개다. 감시시간을1초로 보자는 초기안도 있었으나 확정되지 않았다. 후속 대화의 5초는 예시이고 최종 임계값은 미정이다. Run Enable의 정상 수치도 전사 내용만으로 확정하지 않는다. Vision 검사 결과의0/1 판정 규칙과 서로 다른 필드다.

후속 확인 항목은 마지막 ‘수신’ 시각과 마지막 ‘값 변화’ 시각의 분리, 초기 변화 확인 조건, 실제 폴링 간격과 최대 지연, 토글을 놓치는 경우, 알람/정지 범위, 재연결 후 정상 복귀 및 RESET 조건이다. 통신 정상 판정만으로 장치 전체의 물리적 정상 상태를 보장하지 않는다.

12 DOE 3개와 원빔 5개의 평가 기준

평가 구성은 DOE 장착 Scanner3개와 DOE 없는 원빔 Scanner5개다. 원빔은 16분기 중 하나를 선택한 것이 아니라 Zero Order 위치에서 실제 단일 빔이 출사되는 경우다.

항목Default OffsetFirst Offset
목적Scanner의 기준 위치를 목표 Zero Order에 맞추는 셋업실기판에서 원하는 가공 대응 위치로 이동시키는 셋업
DOE 장착 Head배열 표식으로 기준 중심을 산출하여 Default를 구함실제 가공 배열의 대응 위치를 맞춤
DOE 없는 원빔 Head단일 표식의 실측 중심으로 Default를 구함. 원빔도 셋업 대상DOE의11번 Beam 대응 위치로 원빔을 옮기는 역할
함께 확인할 내용기존 Default 포함 여부와 추천값의 의미Head별 설정·가공 위치·Review 촬영 위치의 일치

추가 통화로 정리된 기준은 모든 Head의 Default는 Zero Order 기준이며, 원빔의11번 Beam 대응 이동을 Default 셋업으로 처리하지 않는다는 것이다. ‘11번’은 DOE 배열과 맞춰 평가할 실제 물리 위치를 뜻하며, 원빔 자체에16개 Beam이 생긴다는 뜻이 아니다.

설정만으로 코드 수정 없이 가능한지는 별도 검증 대상이다. Default 셋업 경로에 First Offset이 같이 적용되는지, 목표 기준이 어떻게 유지되는지부터 확인한다. 특정 오프셋을 자동으로0 초기화하는 절차는 이번 통화에서 확정되지 않았다.

DOE 장착 후보로 양 끝 Head와 중앙 Head가 언급됐지만 최종3개 명단은 확인해야 한다.16분기 Beam Inspection 등 DOE 전용 기능의 사용 범위도 구분한다.

13 Default Offset 최초 표식 탐색과 중심 계산

설계 거리로 Review 위치를 계산해 이동해도 초기에는 표식이 보이지 않을 수 있다. 우선 수동 카메라 Jog로 표식 하나를 확보하고, 그 뒤 DOE 피치에 따른 이웃 탐색과 배열 식별을 자동화하는 방향이 논의됐다.

단계동작 방향확인할 조건
최초 표식 확보가공 후 카메라를 수동 이동하여 보이는 표식 하나를 확보예상 위치와 실제 위치의 차이, FOV·배율·Jog 접근
이웃 탐색DOE 피치에 맞춰 상하좌우로 이동해 표식을 찾음정상 기판·정상 광학 셋업이라는 전제. 미검출 한 번으로 배열 끝 확정하지 않기
배열 식별확보한 표식이 배열의 어느 위치인지 식별방향·Pitch·누락·혼입·중복 위치 검증
중심 산출DOE는 배열의 실측 중심, 원빔은 단일 표식의 중심을 기준으로 사용구체적인 중심 계산식·좌표 변환 확인
추천 Default목표 Zero Order 기준과 실측 기준의 차이로 추천값 산출현재값·추가량·최종값을 구분하고 기존 보정 중복 방지
적용 후 확인새로 가공하고 재측정하여 목표로 이동했는지 검증결과·조건·적용 전후 값을 보관

최초 표식을 찾는 데1~2시간이 걸릴 수도 있다는 현장 설명이 있었다. 이는 초기 셋업의 어려움에 대한 사례이며 목표 탐색시간이나 장비 성능 사양은 아니다.

십자가 크기는5mm와 좌우 합계10mm가 함께 언급돼 전체 길이·반길이를 확인해야 한다. 기존 회의에서 예로 든 ‘Default에5mm를 넣은 상태’와 서로 다른 이야기다. Default에5mm를 넣고 시작했을 때 가공·Review 촬영 위치·추천 최종값에 기존값이 어떻게 포함되는지 검증한다. 배율·가공 조건도 확정값으로 지정하지 않는다.

Default 작업 화면에서 Jog·Beam 간 이동을 함께 제공하고 최초 탐색 좌표·티칭값·추천값·반영값·재가공 결과를 보관한다는 요구를 연결한다. ‘선택 Head만/사용 설정 ON인 Head’의 대상 선택과 ‘전체 일괄/두 Head씩’의 실행 방식, ‘가공만/측정만’의 작업 구분을 명확히 표시한다. 실제 지원 범위와 조건은 확인한다. Head Center·Align Key·기구 거리·Head Gap의 좌표 기준과62/65/3mm 관련 계산도 확인 대상이다.

14 인터넷 제한 현장의 개발 지원과 장애 재현

인터넷이 없는 현장에서 AI가 만든 코드를 개발자가 직접 이해하고 진단할 수 있어야 한다. 로컬 모델만 준비하는 것과 실제 A3 장애를 분석·수정·검증할 수 있는 환경을 갖추는 것은 별도로 확인한다.

분야준비할 내용검증할 점
개발자 이해핵심 로직의 목적·입출력·전제·예외·좌표 단위를 설명하는 주석과 문서담당자가 호출 흐름·인터락·오류 처리와 변경 영향을 설명할 수 있는지
로컬 모델A3 코드·자료에 맞춘 검색과 프로젝트별 개발 지원엉뚱한 코드 분석, 없는 함수 생성, 기존 스타일·예외 정책 위반 여부
Agent 기능필요한 파일을 찾아 수정하고 검증을 이어가는 작업 흐름채팅 답변 외에 실제 수정 범위·diff·컴파일·시험·복원까지 확인
현장 PCCPU/RAM/GPU와 동작 응답을 실제 PC에서 평가소형 모델의 정확도와 처리시간을 실제 A3 과제로 측정
외부 분석승인된 로그로 장애 시점·사용자 조작·장치 응답을 재구성같은 증상이 재현되는지, 부족한 상태가 무엇인지 확인
AI PC 도입현장 성능이 부족하면 별도 사양·운영 방식 검토장비 선정·구매·반입·업데이트 절차는 미확정

소형 모델이 코드 분석에서 부정확한 답을 했다는 경험이 공유됐다. 특정 모델이나 AI PC 도입으로 해결됐다는 결론은 없으며, A3 실제 과제와 현장 사양에 맞춘 평가가 필요하다.

알람 분석기는 알람 선택→전후 Sequence·MELSEC·통신·UI 로그 수집→원인 후보와 근거 안내 흐름으로 검토한다. 가공 분석기는 A1 Script·PLT의 이상 구간과 오차를 분석해 조정 후보·실험 항목을 안내하는 방향이다. 추정 원인과 실제 검증된 원인을 구분한다.

로그는 반출할 수 있을 가능성이 언급됐지만 고객 기술팀·보안 측의 승인 범위는 별도 확정해야 한다. 실제 로그·영상·코드 자료의 수집·보관·반출은 승인된 범위로 준비한다. 외부에서 수정하더라도 승인된 자료만으로 필요한 상황을 얼마나 재현할 수 있는지 시험한다.

15 사용자 조작 이력과 UI 예외 대응

장애 당시 사용자가 어떤 순서로 버튼을 누르고 값을 바꿨는지 추적할 수 있어야 한다. 빠른 중복 클릭이나 다른 메뉴의 동시 조작처럼 일반 사용 흐름 밖의 입력도 시험 대상으로 삼는다.

구분회의 내용후속 검토
텍스트 조작 이력버튼 입력·값 변경·사용자 작업 순서를 남기는 경험 공유시간·화면·대상·변경 전후 값·요청/완료/거절·예외를 연결하는 로그 항목 정의
재생조작을 코드화해 다시 재생한 경험 공유재생기는 검토안. UI 입력만 재현해도 실제 장치 타이밍까지 재현된 것으로 보지 않음
예외 영상예외 전후30초를 저장했던 사례와 용량 문제 공유녹화는 검토안. 저장 길이·용량·보존·보안 승인 미정
중복 클릭딜레이나 버튼 비활성화가 있어도 중복 입력 사례가 있었다는 설명실행 중 재진입·중복 요청·늦은 응답·취소·화면 이동·예외 후 상태 시험
조작 제한처리 중인 작업과 충돌하는 조작을 막을 필요화면 버튼뿐 아니라 동작 상태에서도 중복 실행이 차단되는지 확인
Auto Job Change별도 설명·검토 자리에서 요구사항과 전달 경로 통일 필요확정 요청·설계·문서·담당 간 전달 내용을 하나로 관리
레시피 교육가공 평가 전에 생성 방법과 올바른 입력 자료를 설명할 필요샘플 레시피·생성 절차·확인 기준·담당/교육 일정 정리

특정 기능이 다른 프로젝트에서 동작했다는 사례를 현재 A3 구현 완료로 기록하지 않는다. 저장 공간 제한과 수집·반출 조건을 함께 검토하고, 로그만으로 모든 장애를 해결할 수 있다고 가정하지 않는다.
