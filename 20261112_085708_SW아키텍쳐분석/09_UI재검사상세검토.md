## 발견사항

### UI-R01 · 높음 · 파생 재검사 파일은 BASE의 이미 적용한 측정값을 다시 보정에 쓸 수 있다

**확정된 정적 경로**: `SaveReinspectionRevision`은 BASE 전체 행을 복제하고 선택 행만 교체한다. 미선택 행의 `RESULT_SOURCE=MEASURED`를 `RETAINED`로 바꾸지 않는다. 새 `_REINSP_` 경로는 기존 BASE 경로와 다르다. ReviewData Apply는 `MeasuredRows`가 고른 모든 MEASURED 행을 사용하며 새 결과 경로를 중앙 중복 검사에 전달한다. 재검사 전에 BASE 적용 이력을 확인하거나 BASE와 파생 파일의 공통 측정 식별을 소비하는 UI 코드는 없다.

따라서 BASE의 A/B 측정값으로 이미 보정한 뒤 A만 재검사하여 새 파일을 적용하면, B의 원래 오차가 새 결과의 측정값처럼 다시 누적될 수 있다. 실제 생산 CSV에서 발생했다고 주장하는 것은 아니다. File 담당과 동일 경로를 교차 확인했다.

미실행 검증: BASE A=+0.010/B=+0.020을 1회 적용 → A만 +0.003으로 재검사 → 파생 결과 적용. B가 새로 +0.020 누적되지 않아야 하며 A의 기대 Δ는 재측정 기준과 보정 정책 합의에 따라 명시해야 한다. 같은 파일 재적용 거부, 사용자 명시 재적용, 다음 날짜/이름변경/파생 파일도 분리 시험한다.

### UI-R02 · 중간 · 재검사/저장 중 결과 전환이 오래된 비동기 작업과 겹칠 수 있다

**확정된 구조**: Refresh는 `!IsBusy`, DATA LOAD는 `!IsBusy && !_isDataLoading`만 검사한다. Tree 선택도 실행 중 가드 없이 `Select`한다. 선택/로드는 `ClearLoadedDisplay → ResetReinspectionState`로 Run/Save를 취소하지만 완료를 기다리지 않고 공유 CTS를 Dispose/null, running/saving=false, 목록 비움으로 처리한다. 이전 Run/Save의 progress/catch/finally에는 로드 버전·작업 세대 확인이 없고 공유 CTS/상태/카메라를 다시 갱신한다.

새 결과를 표시한 후 이전 작업의 늦은 progress/종료 상태가 새 화면을 덮을 수 있다. 새 작업까지 빠르게 시작하는 경합에서는 이전 finally가 공유 CTS 필드를 정리할 여지도 있다. 공통 Review lock은 장치 세션 동시 진입을 막으므로 이를 곧바로 "두 축 동시 구동"으로 단정하지 않는다. 실제 타이밍 재현은 미실행이다.

DATA LOAD는 결과의 RecipeId로 현재 Recipe 파일과 현재 Setting을 읽고, 재검사는 이 `_loadedRecipe`와 BASE에 저장된 Shift로 `CreatePlan`한다. CSV 데이터 모델에는 Recipe hash/개정 snapshot이 없다. 목록의 HEAD는 BASE 행에서 고정하지만 실제 검사 point의 HEAD/좌표는 현재 레시피에서 나온다. 같은 Recipe ID의 Head 배정/배치/좌표계가 원검사 이후 바뀐 경우 과거 결과와 새 측정을 섞을 수 있다. 현재 샘플에서 실제 변경/오측정을 입증한 것은 아니다.

### UI-R05 · 낮음 · Beam 후보 고정 16개와 일부 표시/선택 복원은 추가 확인이 필요하다

재검사 Beam 후보는 1~16 고정이고 범위를 벗어난 BASE Beam은 1로 정규화한다. 일반 Review/Fine의 후보는 Recipe split²를 사용한다. 3×3/1×1/다른 지원 분기 수에서는 재검사 UI가 잘못된 후보를 제시할 수 있다. 공통 `ValidateBeamNo`가 실제 허용 범위를 검사하므로 잘못된 Beam이 곧바로 구동된다고 주장하지 않는다. Cell+Shot 중복 제거는 한 Shot에 한 Beam을 선택하는 현재 UI 정책이며, 여러 Beam을 동시에 재검사하는 목록이 아니다. 전용 BEAM_INSPECTION 결과는 재검사 모드에서 명시적으로 제외한다.

이동 완료 progress의 카메라 표시는 일시적으로 `SIMULATION` 고정이고 최종 결과가 돌아온 뒤 REAL/SIM을 바로잡는다. 또한 결과 Tree의 새 `IsSelected` 이벤트는 있으나 record가 `INotifyPropertyChanged`를 선언하지 않는다. 후자는 실제 화면 선택 복원/하이라이트가 갱신되는지 확인할 항목으로 남긴다.

## 비교 결론과 재사용 한계

이전 버전의 단순 결과 조회/Apply에서 **선택 재검사→원본 보존 새 결과→사용자 선택 LOAD**까지 흐름이 확장됐다. 맵 그리기와 로드의 오래된 응답 방어, 같은 결과 파일의 중복 적용 확인, Manual MOF Shift 적용 선택도 실제 연결됐다. 반면 **파생 결과의 측정 소비 계보**, **재검사 작업 중 결과 전환의 수명 관리**, **MOF/BASE 결과와 레시피·기판 소속 확인**은 추가 보완 대상이다.

정적 분석만으로 응답 시간 개선량, 실축 도착/정착, Vision 실제 촬영 성공, 현장 인터락 합격 또는 사용자 회의 요구 전체 구현 완료를 주장할 수 없다. 부모가 수행하는 독립 validation Clone의 빌드/시험 결과와 이 UI 정적 판정을 분리해야 한다.
